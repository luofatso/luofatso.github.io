## 1 编译原理

### 1.1 理解代码到底是什么，计算机如何将代码转换为可以运行的目标程序

::: details 参考

代码是人类可读的、遵循编程语言语法规则的文本。计算机只能理解二进制机器码，代码本质上是程序员与硬件之间的抽象层。

#### 通用编译流水线

源代码 → **词法分析（Lexing/Tokenization）** → Token 流 → **语法分析（Parsing）** → AST（抽象语法树） → **语义分析** → 中间代码 → **优化** → 目标代码（机器码/字节码）

#### 前端相关：V8 的 JIT 编译

JavaScript 是解释型语言，但现代 JS 引擎使用 **JIT（Just-In-Time）编译**：

1. **Ignition（解释器）**：将 AST 转为字节码并解释执行
2. **TurboFan（优化编译器）**：识别"热代码"（频繁执行的函数），将其编译为高度优化的机器码
3. **去优化（Deoptimization）**：当类型假设被推翻时，回退到解释执行

> V8 的"热代码检测"机制意味着函数被调用越多，执行越快。这也是为什么 V8 偏好"单态"（始终同类型）的代码 -- 类型变化会触发去优化。

#### 前端工具链中的"编译"

- **Babel**：源码到源码的转译器。解析 JS → AST → 按插件转换 AST 节点 → 生成兼容代码
- **TypeScript**：TS 源码 → AST → 类型检查 → 擦除类型 → JS 输出
- **webpack**：构建依赖图 → 生成 bundle 输出（本质是代码生成步骤）
- **Vite**：开发阶段用 esbuild（Go 编写）做快速转译，生产用 Rollup

#### 实践意义

当你写 `const x = 1`，V8 分词得到 `[Keyword, Identifier, Punctuator, NumericLiteral, Punctuator]`，解析器构建 AST，再转字节码执行。理解这个流程有助于区分**解析期错误**（如 `Unexpected token`）和**运行时错误**。

:::

### 1.2 正则表达式的匹配原理和性能优化

::: details 参考

#### 正则引擎类型

| 类型                        | 特点                                        | 使用场景                           |
| --------------------------- | ------------------------------------------- | ---------------------------------- |
| **DFA**（确定有限自动机）   | 文本主导、无回溯、始终 O(n)、不支持反向引用 | `awk`、`egrep`                     |
| **NFA**（非确定有限自动机） | 正则主导、有回溯、支持惰性量词和反向引用    | **JavaScript**、Java、Python、Perl |

前端开发者需要理解的是 NFA 引擎的**回溯机制**。

#### 回溯机制

NFA 一次尝试一条路径，匹配失败时回退到上一个决策点换一条路径重试：

- **贪婪量词** `*` `+`：先尽可能多地匹配，然后逐字符回退
- **惰性量词** `*?` `+?`：先尽可能少匹配，然后逐步扩展
- **占有量词** `*+` `++`：尽可能多匹配，**永不回退**（JavaScript 原生不支持）

#### 灾难性回溯（Catastrophic Backtracking）

```javascript
// 危险模式：嵌套量词
/(a+)+b/.test('aaaaaaaaaaaaaaaaaaaaac')  // 指数级时间复杂度！

// 真实案例：URL 匹配
/(\/[\w-]+)+/.test('/a/b/c/d/e/f/g/h/i/j/no-match')
```

引擎会穷尽所有分割 `a` 字符串的方式，时间复杂度达到 O(2^n)。

#### JS 中正则性能优化

| 建议                       | 说明                                          |
| -------------------------- | --------------------------------------------- |
| 避免嵌套量词               | `(a+)+` `(a*)*` 是危险信号                    |
| 避免多选歧义               | `/(a\|ab)bc/` 匹配 `abc` 需要回溯             |
| 用非捕获组 `(?:...)`       | 不需要 `$1` 时避免捕获开销                    |
| 用字符类代替多选           | `/[aeiou]/` 快于 `/(a\|e\|i\|o\|u)/`          |
| 避免 `.*` 在模式开头       | 导致过度回溯；用锚点 `^` 正向匹配             |
| 用 `test()` 取代 `match()` | 只需布尔结果时不构建结果数组                  |
| 预编译正则                 | 循环外存储正则字面量，避免反复 `new RegExp()` |

#### 前端常见应用

```javascript
// 邮箱校验
const emailRe = /^[^\s@]+@[^\s@]+\.[^\s@]+$/

// SPA 路由匹配
const pathRe = /^\/users\/(\d+)\/posts\/([\w-]+)$/
const [, uid, slug] = '/users/42/posts/hello-world'.match(pathRe)

// 模板插值
'Hello {{name}}'.replace(/\{\{([^}]+)\}\}/g, (_, key) => data[key])
```

### 1.3 如何将JavaScript代码解析成抽象语法树(AST)

::: details 参考

#### 什么是 AST

AST 是源代码的**树状结构表示**，每个节点代表一个语法构造（变量声明、函数调用、字面量等）。AST 剥离了格式细节（空格、注释），只保留语义结构。

#### JS 代码到 AST 的流程

1. **词法分析（Tokenizer/Lexer）**：拆分源代码为 Token 流
   ```
   "const x = 42;" → [Keyword, Identifier, Punctuator, NumericLiteral, Punctuator]
   ```
2. **语法分析（Parser）**：消费 Token 流，应用 ECMAScript 语法规则，生成 AST 节点

#### 主流 JS 解析器

| 工具                            | 特点                                 |
| ------------------------------- | ------------------------------------ |
| **ESTree**                      | 社区标准 AST 规范，ESLint/Babel 遵循 |
| **@babel/parser**（原 Babylon） | 支持 JSX、TS、Flow、Stage 提案       |
| **Acorn**                       | 轻量快速，webpack 内部使用           |
| **Esprima**                     | 最早的 JS 解析器之一，ETree 兼容     |
| **TypeScript Compiler API**     | 微软出品，含类型信息                 |

#### 常见 AST 节点类型

`Program`（根）、`VariableDeclaration`、`FunctionDeclaration`、`ArrowFunctionExpression`、`CallExpression`、`MemberExpression`、`Literal`、`Identifier`、`IfStatement`、`BinaryExpression`、`TemplateLiteral`、`ImportDeclaration`

#### AST 遍历与操作

- **Visitor 模式**：遍历节点时触发 enter/exit 回调
- **修改节点**：替换、插入兄弟节点、删除节点
- **代码生成**：将修改后的 AST 转回代码字符串

#### 实践：写一个 Babel 插件

```javascript
import { parse } from '@babel/parser'
import traverse from '@babel/traverse'
import generate from '@babel/generator'

const code = 'const foo = bar(1, 2);'
const ast = parse(code)

traverse(ast, {
  CallExpression(path) {
    console.log('函数调用:', path.node.callee.name) // "bar"
  }
})

const output = generate(ast).code // "const foo = bar(1, 2);"
```

> 在线工具 [AST Explorer](https://astexplorer.net) 是理解和调试 AST 的最重要工具，支持多种解析器和语言。

#### AST 在前端工具链中的应用

- **Babel 插件**：如 `transform-arrow-functions` 把箭头函数转为普通函数
- **ESLint 规则**：如 `no-console` 检测 `console.log` 调用并报错
- **Prettier**：解析 → AST → 丢弃原格式 → 用统一规则重新生成
- **代码压缩（Terser/UglifyJS）**：遍历 AST 做名称混淆和死代码消除

### 1.4 base64的编码原理

::: details 参考

#### 是什么，为什么

Base64 将二进制数据编码为 64 个可打印 ASCII 字符（A-Z、a-z、0-9、`+`、`/`，`=` 填充）。目的是让二进制数据安全地通过**只支持文本的协议**（如 JSON、XML、HTTP 头、SMTP 邮件）。

#### 编码算法（核心原理）

1. 输入二进制数据，按字节（8 位）分组
2. 每 3 字节（24 位）为一组
3. 将 24 位拆分为 4 个 6 位组（$2^6 = 64$ 种可能值）
4. 每个 6 位值映射到 Base64 字母表的一个字符
5. 输入不足 3 字节时：缺 1 字节补 1 个 `=`，缺 2 字节补 2 个 `=`

**示例：编码 "Man"**

```
M (0x4D=77)  a (0x61=97)  n (0x6E=110)
01001101    01100001     01101110
010011  010110  000101  101110
19(T)   22(W)   5(F)    46(u)
→ "TWFu"
```

#### 容量开销

Base64 使数据增大约 **33%**（每 3 字节变成 4 字符）。这对前端决策有直接影响：

- 小于 1KB 的小图标 → 适合内联为 data URL，减少 HTTP 请求
- 大图片 → 应单独请求，不内联

#### JavaScript API

```javascript
// 基础用法（仅支持 Latin-1 字符）
btoa('hello') // "aGVsbG8="
atob('aGVsbG8=') // "hello"

// Unicode 安全编码
function utf8ToBase64(str) {
  return btoa(
    encodeURIComponent(str).replace(/%([0-9A-F]{2})/g, (_, p1) => String.fromCharCode('0x' + p1))
  )
}

function base64ToUtf8(str) {
  return decodeURIComponent(
    atob(str)
      .split('')
      .map((c) => '%' + ('00' + c.charCodeAt(0).toString(16)).slice(-2))
      .join('')
  )
}
```

#### 前端常见使用场景

| 场景               | 说明                                                  |
| ------------------ | ----------------------------------------------------- |
| **Data URL**       | `<img src="data:image/png;base64,iVBOR...">` 内联小图 |
| **文件预览**       | `FileReader.readAsFile()` 上传前预览图片              |
| **Canvas 导出**    | `canvas.toDataURL()` 返回 Base64 数据 URL             |
| **Service Worker** | 缓存 Base64 编码的响应体                              |
| **Web Crypto**     | 将 `ArrayBuffer` 加密结果转 Base64 传输               |

#### 变体：Base64URL

JWT 等 URL 场景中：`+` → `-`，`/` → `_`，省略 `=` 填充。

### 1.5 几种进制的相互转换计算方法，在JavaScript中如何表示和转换

::: details 参考

#### 常见进制

| 进制     | 基数 | 数字范围 | JS 字面量 | 前端场景                     |
| -------- | ---- | -------- | --------- | ---------------------------- |
| 二进制   | 2    | 0,1      | `0b1010`  | 位运算、权限掩码             |
| 八进制   | 8    | 0-7      | `0o755`   | Unix 文件权限                |
| 十进制   | 10   | 0-9      | `42`      | 日常使用                     |
| 十六进制 | 16   | 0-9,A-F  | `0xFF`    | CSS 颜色、内存地址、加密哈希 |

#### JavaScript 中的转换

**数字 → 字符串（任意进制）**：

```javascript
;(255).toString(2) // "11111111"
;(255).toString(16) // "ff"
;(255).toString(8) // "377"
// toString(radix) 支持 radix 2~36
```

**字符串 → 数字**：

```javascript
parseInt('ff', 16) // 255 —— 永远传第二个参数！
parseInt('11111111', 2) // 255
Number('0xFF') // 255 （检测 hex 前缀）
;+'0xFF' // 255
```

> `parseInt` 不传 radix 有坑：`parseInt('08')` 在老引擎中可能返回 0（把前导 0 当作八进制前缀）。

#### 手动转换算法

- **十进制转 N 进制**：反复除以 N，取余数，逆序排列
  - `42` → 十六进制：42÷16=2 余 10(A)，2÷16=0 余 2 → `0x2A`
- **N 进制转十进制**：每位数字 × $N^{position}$，求和
  - `0x2A` = $2 × 16^1 + 10 × 16^0$ = 32 + 10 = 42

#### 前端实战

```javascript
// Hex 颜色 ↔ RGB
const hexToRgb = (hex) => ({
  r: parseInt(hex.slice(1, 3), 16),
  g: parseInt(hex.slice(3, 5), 16),
  b: parseInt(hex.slice(5, 7), 16)
})

const rgbToHex = (r, g, b) => `#${((1 << 24) + (r << 16) + (g << 8) + b).toString(16).slice(1)}`

// 权限位掩码
const READ = 0b001 // 1
const WRITE = 0b010 // 2
const DELETE = 0b100 // 4
let perm = READ | WRITE // 0b011 = 3
const canRead = (perm & READ) !== 0 // true
const canDelete = (perm & DELETE) !== 0 // false

// 简单 UUID 生成
const uuid = () =>
  'xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx'.replace(/[xy]/g, (c) =>
    ((Math.random() * 16) | (c === 'x' ? 0 : 0x8)).toString(16)
  )
```

:::

## 2 网络协议

### 2.1 理解什么是协议，了解TCP/IP网络协议族的构成，每层协议在应用程序中发挥的作用

::: details 参考

#### 什么是协议

协议是通信双方约定的规则集合，定义数据格式、时序、顺序和错误处理。如同语言：两边必须遵循相同约定才能正确交流。

#### TCP/IP 四层模型（前端该关注的视角）

| 层             | 核心协议                    | 前端关联                                                  |
| -------------- | --------------------------- | --------------------------------------------------------- |
| **应用层**     | HTTP、HTTPS、WebSocket、DNS | 这是前端代码的工作层。`fetch()`、XHR、WebSocket API       |
| **传输层**     | TCP、UDP                    | TCP 可靠性决定资源加载质量；连接握手 + 慢启动影响首页速度 |
| **网络层**     | IP、ICMP、ARP               | IP 路由决定数据包路径；CDN 基于 IP 就近选边缘节点         |
| **网络接入层** | 以太网、Wi-Fi、4G/5G        | 物理传输。移动网络延迟差异大（3G ~200ms vs 5G ~5ms RTT）  |

#### 数据封装（Data Encapsulation）

每层把自己的头部加到上层数据前，像嵌套信封：

```
HTTP 请求 → [HTTP 数据]
      ↓ TCP 封装
[TCP 头 + HTTP 数据]（段/Segment）
      ↓ IP 封装
[IP 头 + TCP 头 + HTTP 数据]（包/Packet）
      ↓ 链路层封装
[帧头 + IP 头 + TCP 头 + HTTP 数据 + 帧尾]（帧/Frame）
```

#### DevTools 中的体现

Chrome DevTools Network 面板的 Timing 分解直接对应各层：

- **DNS Lookup** → 应用层
- **Initial connection** → 传输层（TCP 握手 + TLS 握手）
- **Request sent / Waiting (TTFB)** → 应用层数据往返
- `net::ERR_CONNECTION_REFUSED` → 传输层错误（端口无监听）
- `net::ERR_NAME_NOT_RESOLVED` → 应用层 DNS 错误

#### 性能影响

- TCP 连接建立需要 1 RTT（Round Trip Time），跨洋可能 200-300ms
- HTTP/3 使用 QUIC（基于 UDP）替代 TCP 来消除连接建立开销
- `navigator.connection` API 提供 `effectiveType`（4g/3g/2g）、`rtt`、`downlink`，可用于自适应加载

:::

### 2.2 三次握手和四次挥手详细原理，为什么要使用这种机制

::: details 参考

#### 三次握手（连接建立）

```
Client                         Server
  |                              |
  |--- SYN, seq=x ------------->|  (1) 客户端：SYN_SENT
  |                              |
  |<-- SYN+ACK, seq=y, ack=x+1 -|  (2) 服务端：SYN_RCVD
  |                              |
  |--- ACK, seq=x+1, ack=y+1 -->|  (3) 双方：ESTABLISHED
  |                              |
```

**为什么是 3 次而不是 2 次？**

防止历史连接请求导致半开连接。如果网络中滞留了一个旧的 SYN 包，服务端收 SYN 后直接进入连接状态，但客户端并未发起新连接——服务端资源泄漏。第三次 ACK 让服务端确认：客户端确实需要这次连接。

**为什么双方都要同步序列号？**

TCP 是全双工的——双方都需要初始序列号（ISN），确保后续数据传输能正确编号和确认。

> **DevTools 视角**：Chrome Network 中 "Initial connection" = 1.5 RTT（SYN + SYN-ACK + ACK）。DNS 解析在握手之前。

#### 四次挥手（连接断开）

```
Client                             Server
  |                                  |
  |--- FIN, seq=u ---------------->|  (1) 主动方：FIN_WAIT_1
  |                                  |
  |<-- ACK, seq=v, ack=u+1 --------|  (2) 被动方：CLOSE_WAIT，主动方：FIN_WAIT_2
  |                                  |
  |<-- FIN, ACK, seq=w, ack=u+1 ---|  (3) 被动方：LAST_ACK
  |                                  |
  |--- ACK, seq=u+1, ack=w+1 ----->|  (4) 主动方：TIME_WAIT，被动方：CLOSED
  |                                  |
```

**为什么是 4 次而不是 3 次？**

TCP 是全双工——每个方向的通道需要**独立关闭**。收到对方的 FIN 意味着"对方不发了"，但我方可能还有数据要发，所以我方的 FIN 可能在 ACK 之后单独发送。因此 ACK 和第 3 步的 FIN 不能合并。

**TIME_WAIT 状态**：主动关闭方等待 2×MSL（Maximum Segment Lifetime，通常 2 分钟），确保：

1. 对端收到最后的 ACK（若对端没收到，会重传 FIN）
2. 该连接的滞留包在网络中完全消失

#### 前端关联

| 知识点              | 影响                                                                        |
| ------------------- | --------------------------------------------------------------------------- |
| **Keep-Alive**      | HTTP/1.1 默认复用 TCP 连接，避免重复握手开销                                |
| **6 连接限制**      | HTTP/1.1 每域名最多 6 并发连接（过去用域名分片突破，HTTP/2 后已不需要）     |
| **端口耗尽**        | 本地频繁重启 dev server 可能遇 `address already in use`——TIME_WAIT 持有端口 |
| **HTTP/2 多路复用** | 一个连接承载所有请求，连接数需求大幅降低                                    |

:::

### 2.3 有哪些协议是可靠，TCP有哪些手段保证可靠交付

::: details 参考

#### 可靠 vs 不可靠协议

| 类型       | 协议 | 特性                         | 前端场景                                         |
| ---------- | ---- | ---------------------------- | ------------------------------------------------ |
| **可靠**   | TCP  | 有序、无丢失、无重复、无损坏 | HTTP、HTTPS、WebSocket、文件传输                 |
| **不可靠** | UDP  | 无送达保障，但低延迟         | DNS（主要）、WebRTC 媒体流、QUIC/HTTP3、在线游戏 |

#### TCP 可靠性的五大支柱

**① 序列号与确认（Sequence & Acknowledgment）**

每个字节都有编号。接收方发送 ACK 告知"期望的下一个字节序号"。

```
发送方：字节 1-1000，seq=1，len=1000
接收方：ACK ack=1001（"收到了 1-1000，下一个发 1001"）
```

**② 校验和（Checksum）**

TCP 头部 16 位校验和覆盖伪首部 + TCP 头 + 数据。校验失败则静默丢弃该段（不发 ACK），触发重传。

**③ 重传机制**

- **超时重传**：发送后启动定时器，超时（RTO，基于 RTT 动态计算）未收到 ACK 则重发
- **快速重传**：发送方收到 3 个重复 ACK（说明后续包已到，中间丢了一个），不等超时立即重传

**④ 流量控制（Flow Control / 滑动窗口）**

接收方通告"窗口大小"（还能收多少字节）。发送方未被确认的数据量不能超过窗口大小。防止快发送方淹没慢接收方。

> 前端类比：Web Streams API 的背压机制（`ReadableStream.pipeTo` 的反压）、`requestAnimationFrame` 的帧率节流。

**⑤ 拥塞控制（Congestion Control）**

- **慢启动**：拥塞窗口 cwnd 从小开始，每 RTT 翻倍增长
- **拥塞避免**：达到阈值后线性增长
- **丢包后**：乘性减半（AIMD：Additive Increase Multiplicative Decrease）

> 这就解释了为什么页面资源加载速度呈"加速曲线"——前几个 KB 是最慢的（慢启动），这也是 HTTP/2 优先级和 `preload` 如此重要的原因。

#### 前端影响总结

| 机制     | 解决的问题 | 前端感知                   |
| -------- | ---------- | -------------------------- |
| Seq/ACK  | 丢包、乱序 | 保证 HTML/CSS/JS 完整到达  |
| 校验和   | 数据损坏   | 避免损坏资源               |
| 重传     | 包丢失     | DevTools 中 "stalled" 请求 |
| 流量控制 | 接收方溢出 | 保护移动端弱设备           |
| 拥塞控制 | 网络拥堵   | 首页初始加载偏慢（慢启动） |

:::

### 2.4 DNS的作用、DNS解析的详细过程，DNS优化原理

::: details 参考

#### DNS 是什么

互联网的"电话簿"：将人类可读域名（`api.example.com`）翻译为机器可路由的 IP 地址（`93.184.216.34`）。使用 UDP 端口 53（单次查询/响应小，无需 TCP 握手开销），必要时回退到 TCP（响应过大时）。

#### 完整递归解析过程

```
1. 浏览器 DNS 缓存 ──命中→ 直接返回
        ↓ 未命中
2. OS DNS 缓存（hosts 文件、系统解析器缓存）
        ↓ 未命中
3. 路由器缓存
        ↓ 未命中
4. ISP 递归解析器（如 8.8.8.8 / 1.1.1.1）
        ↓
5. 根域名服务器 → 返回 .com TLD 服务器地址
        ↓
6. .com TLD 服务器 → 返回 example.com 权威服务器地址
        ↓
7. example.com 权威服务器 → 返回 api.example.com 最终 IP
```

#### DNS 记录类型（前端相关）

| 记录      | 用途                                                                          |
| --------- | ----------------------------------------------------------------------------- |
| **A**     | 域名 → IPv4 地址                                                              |
| **AAAA**  | 域名 → IPv6 地址                                                              |
| **CNAME** | 域名 → 另一个域名（别名）。CDN 常用：`cdn.example.com` → `xxx.cloudfront.net` |
| **TXT**   | 任意文本。Google Search Console 验证、SPF 邮件策略                            |

#### DevTools 中的 DNS 诊断

Network 瀑布图中 **DNS Lookup** 时间如果过大，排查方向：

- ISP DNS 服务器慢（尝试切换 8.8.8.8 / 1.1.1.1）
- 页面引用了太多不同域名（每个唯一域名都需要单独 DNS 查询）
- 无意义的重定向导致额外 DNS 查询

#### DNS 优化技巧

```html
<!-- 1. dns-prefetch：提前解析关键第三方域名（开销极低） -->
<link rel="dns-prefetch" href="//api.example.com" />
<link rel="dns-prefetch" href="//cdn.example.com" />

<!-- 2. preconnect：DNS + TCP + TLS 一步到位（开销较大，限 4-6 个） -->
<link rel="preconnect" href="https://api.example.com" />
```

- **减少唯一域名数**：HTTP/2 支持单连接多路复用，应合并域名而非分片
- **CDN DNS 路由（GeoDNS）**：同一域名 `cdn.example.com` 根据用户 DNS 解析器的地理位置返回不同边缘节点 IP
- **HTTP/3 连接迁移**：QUIC 连接可在切换网络（Wi-Fi ↔ 蜂窝）时保持，无需重新 DNS + 握手

:::

### 2.5 CDN的作用和原理

::: details 参考

#### 什么是 CDN

Content Delivery Network（内容分发网络）：地理上分布在全球的边缘代理服务器网络，就近为用户提供内容缓存服务。核心目的：**降低延迟**、**减轻源站负载**、**吸收 DDoS 攻击**。

#### 核心工作机制

```
用户请求 cdn.example.com
  ↓ DNS 就近路由
最近边缘节点
  ├─ 缓存命中 → 直接返回
  └─ 缓存未命中 → 回源获取 → 缓存 → 返回用户
                     ↑ 可选中间层（Origin Shield）
```

- **DNS 就近路由**：同一域名返给不同用户的 IP 不同（基于 DNS 解析器 IP 的地理位置）
- **Anycast**：多个服务器共享同一 IP，BGP 自动路由到最近节点

#### 前端 CDN 部署模式

**① 内容哈希 + 永久缓存（最佳实践）**

```nginx
# 带 hash 的静态资源：永久缓存
Cache-Control: public, max-age=31536000, immutable
```

```
/static/js/main.a3f2b1c.js   # 文件名含内容 hash
/static/css/app.9e8d7f6.css
```

代码变更 → 文件名变化 → CDN 视作新文件自动回源。**文件名即版本号**。

**② HTML 入口文件不缓存**

```nginx
Cache-Control: no-cache   # 每次都重新验证
```

HTML 必须始终新鲜，指向最新的 hash 资源。

**CDN 缓存失效**（CDN Invalidation / Purge）：手动清除边缘节点缓存。应为**应急手段**而非常规策略，首选用内容哈希。

#### 进阶 CDN 功能

| 功能          | 说明                                                                  |
| ------------- | --------------------------------------------------------------------- |
| **图片优化**  | 边缘实时缩放、格式转换（WebP/AVIF）、压缩（`?width=800&format=webp`） |
| **边缘计算**  | Cloudflare Workers、Lambda@Edge — A/B 测试、地域定制、轻量 API        |
| **DDoS 防护** | 分布式节点吸收流量攻击                                                |
| **SSL 终结**  | 边缘节点处理 TLS 握手，用户到边缘距离短，握手快                       |

#### 前端开发者 CDN 清单

- 静态资源带 hash → immutable 缓存策略
- HTML 入口 → `no-cache` 或短 TTL
- HTML 不在 CDN 时，用 `preconnect` 预热 CDN 域名
- 配置 CORS 头（CDN 域名与站点域名不同时）
- 关注缓存命中率（目标 > 95%）
- 开启 CDN 访问日志便于排查

:::

### 2.6 HTTP请求报文和响应报文的具体组成，能理解常见请求头的含义，有几种请求方式，区别是什么

::: details 参考

#### 请求报文结构

```
POST /api/users?role=admin HTTP/1.1     ← 请求行（方法 + URI + 版本）
Host: api.example.com                   ← 首部
Accept: application/json
Authorization: Bearer eyJhbG...
Content-Type: application/json
User-Agent: Mozilla/5.0 ...
Cookie: session_id=abc123
                                         ← 空行（CRLF，必须）
{"name": "John", "email": "a@b.com"}    ← 主体（GET/HEAD 无）
```

#### 响应报文结构

```
HTTP/1.1 200 OK                          ← 状态行（版本 + 状态码 + 原因短语）
Content-Type: application/json
Content-Length: 1234
Cache-Control: public, max-age=3600
Access-Control-Allow-Origin: *
Set-Cookie: session=xyz; HttpOnly; Secure; SameSite=Lax
                                         ← 空行
{"data": [...]}                          ← 主体
```

#### 核心请求头（前端视角）

| 头部                 | 用途                                                  |
| -------------------- | ----------------------------------------------------- |
| `Host`               | 目标域名（HTTP/1.1 必填）                             |
| `Accept`             | 期望的响应类型 `application/json`                     |
| `Content-Type`       | 请求体格式 `application/json` / `multipart/form-data` |
| `Authorization`      | 认证令牌 `Bearer <JWT>`                               |
| `Cookie`             | 浏览器自动附带已存 Cookie                             |
| `Origin` / `Referer` | 请求来源——CORS 和 CSRF 防御依赖                       |
| `Cache-Control`      | 缓存控制 `no-cache` / `max-age=0`                     |
| `If-None-Match`      | 条件请求（ETag）——304 优化                            |
| `Accept-Encoding`    | 压缩支持 `gzip, deflate, br`                          |

#### 核心响应头（前端视角）

| 头部                          | 用途                                           |
| ----------------------------- | ---------------------------------------------- |
| `Content-Type`                | 响应体 MIME 类型，匹配 `fetch().json()` 期望   |
| `Content-Encoding`            | 压缩算法 `gzip` / `br`                         |
| `Cache-Control`               | 缓存策略 `public, max-age=31536000, immutable` |
| `ETag`                        | 内容指纹——条件请求验证                         |
| `Set-Cookie`                  | 设置 Cookie，配合 `HttpOnly; Secure; SameSite` |
| `Access-Control-Allow-Origin` | CORS 许可域                                    |
| `Content-Security-Policy`     | XSS 防御策略                                   |
| `Location`                    | 301/302 重定向目标                             |

#### HTTP 方法

| 方法        | 语义           | 幂等 | 安全 | 有主体 | 前端用途               |
| ----------- | -------------- | ---- | ---- | ------ | ---------------------- |
| **GET**     | 获取资源       | ✓    | ✓    | ✗      | API 数据获取、页面导航 |
| **POST**    | 创建资源       | ✗    | ✗    | ✓      | 表单提交、登录、新建   |
| **PUT**     | 完整替换       | ✓    | ✗    | ✓      | 整对象更新             |
| **PATCH**   | 部分更新       | ✗    | ✗    | ✓      | 指定字段更新           |
| **DELETE**  | 删除资源       | ✓    | ✗    | 可选   | 移除数据               |
| **HEAD**    | 无响应体的 GET | ✓    | ✓    | ✗      | 检查资源是否存在       |
| **OPTIONS** | 预检请求       | ✓    | ✓    | ✗      | 浏览器 CORS 前自动发送 |

> **幂等**：多次相同请求效果与一次相同。POST 非幂等——提交两次表单 = 两条记录。
> **安全**：不修改服务器状态。仅 GET、HEAD、OPTIONS。

### 2.7 HTTP所有状态码的具体含义，看到异常状态码能快速定位问题

::: details 参考

#### 1xx 信息

| 状态码                    | 含义                               | 前端场景                     |
| ------------------------- | ---------------------------------- | ---------------------------- |
| `100 Continue`            | 服务器已收请求头，客户端可继续发体 | 大文件分块上传               |
| `101 Switching Protocols` | 协议升级                           | WebSocket 握手响应           |
| `103 Early Hints`         | 提前发送预加载链接                 | Chrome 103+ 替代 Server Push |

#### 2xx 成功

| 状态码                | 含义       | 前端场景                                |
| --------------------- | ---------- | --------------------------------------- |
| `200 OK`              | 标准成功   | GET/PUT 默认响应                        |
| `201 Created`         | 资源已创建 | POST 成功，`Location` 头指向新资源      |
| `204 No Content`      | 成功但无体 | DELETE 常见，`fetch().text()` 返回 `""` |
| `206 Partial Content` | 分块响应   | Range 请求（视频拖拽、断点续传）        |

#### 3xx 重定向

| 状态码                   | 含义       | 关键行为                                      |
| ------------------------ | ---------- | --------------------------------------------- |
| `301 Moved Permanently`  | 永久重定向 | 浏览器缓存，搜索引擎更新链接                  |
| `302 Found`              | 临时重定向 | POST → GET（body 丢失），常见于表单提交后跳转 |
| `304 Not Modified`       | 未修改     | 条件请求命中，无 body 传输，**带宽为零**      |
| `307 Temporary Redirect` | 临时重定向 | 方法/Body **保持不变**                        |
| `308 Permanent Redirect` | 永久重定向 | 方法/Body **保持不变**                        |

#### 4xx 客户端错误

| 状态码                       | 含义              | 排查方向                                |
| ---------------------------- | ----------------- | --------------------------------------- |
| `400 Bad Request`            | 请求格式错误      | 检查 JSON 语法、必填字段、Content-Type  |
| `401 Unauthorized`           | 未认证            | Token 过期/缺失，跳转登录页             |
| `403 Forbidden`              | 无权限            | 已认证但权限不足，**不要**跳转登录      |
| `404 Not Found`              | 资源不存在        | 检查 URL 路径、资源 ID，UI 友好提示     |
| `405 Method Not Allowed`     | 方法错误          | GET vs POST，检查 API 文档              |
| `408 Request Timeout`        | 服务器等待超时    | 上传太慢、服务器超时配置                |
| `409 Conflict`               | 资源冲突          | 乐观锁冲突（并发编辑同一数据）          |
| `413 Payload Too Large`      | 请求体过大        | 文件上传超过限制，加前端体积校验        |
| `414 URI Too Long`           | URL 过长          | GET 请求参数太多，改用 POST             |
| `415 Unsupported Media Type` | Content-Type 错误 | 发 XML 但服务器要 JSON                  |
| `422 Unprocessable Entity`   | 语义错误          | JSON 格式正确但字段值不合法（校验失败） |
| `429 Too Many Requests`      | 速率受限          | 实现指数退避重试，前端提示"稍后再试"    |

#### 5xx 服务器错误

| 状态码                      | 含义             | 排查方向                          |
| --------------------------- | ---------------- | --------------------------------- |
| `500 Internal Server Error` | 服务器崩溃       | 查服务端日志，前端显示通用错误 UI |
| `502 Bad Gateway`           | 上游返回无效响应 | 常见于 nginx 后的服务重启期间     |
| `503 Service Unavailable`   | 暂时不可用       | 过载或维护，指数退避重试          |
| `504 Gateway Timeout`       | 上游响应超时     | 长耗时 API、数据库查询超时        |

#### 前端错误处理模式

```javascript
async function request(url, options) {
  const res = await fetch(url, options)
  if (!res.ok) {
    if (res.status === 401) {
      /* 跳登录 */
    } else if (res.status === 403) {
      /* 提示无权限 */
    } else if (res.status === 429) {
      /* 退避重试 */
    } else if (res.status >= 500) {
      /* 上报监控 + 通用错误 */
    }
    throw new ApiError(res.status, await res.text())
  }
  return res.json()
}
```

### 2.8 HTTP1.1、HTTP2.0带来的改变

::: details 参考

#### HTTP/1.1 的特点与痛点

| 痛点                         | 原因                                                       | 前端的"奇技淫巧"      |
| ---------------------------- | ---------------------------------------------------------- | --------------------- |
| **队头阻塞（HOL Blocking）** | 同一连接请求必须按序处理，一个慢响应卡住全部               | 浏览器开 6 个并发连接 |
| **Header 不压缩**            | 每次请求都完整发送头部（Cookie、UA 等），重复 500-800 字节 | 无解                  |
| **文本协议**                 | 冗长、解析低效                                             | 无解                  |

**HTTP/1.1 时代的优化 hack**（在 HTTP/2 下反而有害）：

- **域名分片**：`static1.xx.com`、`static2.xx.com` 突破 6 连接限制 → HTTP/2 下单连接就够，多域名反而增加 DNS + 握手开销
- **CSS Sprites**：所有小图合一张大图，`background-position` 裁切 → HTTP/2 多路复用后，独立小图更灵活
- **JS/CSS 合并打包**：一个 `bundle.js` → HTTP/2 下按需按模块拆包更优，实现细粒度缓存
- **内联（Inlining）**：CSS/JS/SVG 内嵌 HTML → 无法独立缓存，增加 HTML 体积

#### HTTP/2 核心改进

**① 多路复用（Multiplexing）** —— 关键特性

一次 TCP 连接上同时传输多个请求/响应。每个请求/响应被拆分为帧（frame），交叉发送，通过 Stream ID 在接收端重组。消除了**应用层**队头阻塞。

**② Header 压缩（HPACK）**

使用静态表（预定义的常见头 → 索引号）+ 动态表（记住之前出现的 header 组合）。后续请求只发索引号而非完整 header 字符串。大型 Cookie 的开销急剧降低。

**③ 二进制分帧**

HTTP/2 是二进制协议（非文本），解析更快、更少出错。对 `fetch()` 完全透明。

**④ Server Push**

服务端主动推送客户端未来可能需要的资源。Chrome 2022 年已移除支持（推送过度浪费带宽）。`103 Early Hints` 是更现代的替代。

**⑤ 流优先级与流控**

客户端可告知服务端优先级（"先发 CSS，后发图片"），支持逐流流控避免单一流独占连接。

#### HTTP/1.1 vs HTTP/2 策略迁移

| HTTP/1.1 策略    | HTTP/2 策略         |
| ---------------- | ------------------- |
| 域名分片         | 合并为一个域名      |
| CSS Sprites      | 独立小图            |
| JS/CSS 全量合并  | Code-split 按需加载 |
| 内联关键 CSS     | 103 Early Hints     |
| Cookie-free 域名 | HPACK 压缩下不需要  |

#### HTTP/3 (QUIC) 简览

- 基于 **UDP** 替代 TCP，消除 TCP 层队头阻塞
- 内置 TLS 1.3 加密
- 连接迁移：切换网络（Wi-Fi ↔ 蜂窝）连接不中断
- 0-RTT 恢复连接（重复连接时）

:::

### 2.9 HTTPS的加密原理，如何开启HTTPS，如何劫持HTTPS请求

::: details 参考

#### 为什么需要 HTTPS

HTTP 是明文传输，同网络（Wi-Fi、ISP）的任何人可阅读和篡改。HTTPS 提供三个保证：

- **机密性（Confidentiality）** —— 加密传输，无法窃听
- **完整性（Integrity）** —— 数据未被篡改
- **身份验证（Authentication）** —— 确认对方是真实的服务器

> Service Worker、Geolocation API、HTTP/2 等新能力都需要 Secure Context（HTTPS 或 localhost）。

#### 混合加密模型：非对称 + 对称

**非对称加密（TLS 握手阶段）**：公钥/私钥对。公钥加密，私钥解密。作用是**安全交换对称密钥 + 验证服务器身份**。速度慢，不能用于大量数据。
→ RSA、ECDHE（推荐，支持前向保密）

**对称加密（数据传输阶段）**：同一密钥加密解密。速度快。
→ AES-GCM（带身份验证的加密）

**HMAC（消息认证码）**：检测数据是否被篡改。

#### TLS 1.3 握手过程（简化）

```
1. ClientHello  → 支持的密码套件、TLS 版本、随机数、密钥共享
2. ServerHello  ← 选中密码套件、随机数、密钥共享、证书（含服务器公钥）
3. 认证         → 客户端验证证书链（CA 签名 → 中间 CA → 根 CA）
4. 密钥协商     → 双方通过 ECDHE 独立计算相同的会话密钥
                  ★ 前向保密：即使服务器私钥泄露，历史会话密钥无法还原
5. Finished     → 双方确认握手完成，切换对称加密通信
```

> TLS 1.3 = 1-RTT 握手，TLS 1.2 = 2-RTT。重复连接可 0-RTT 恢复。

#### 证书与 PKI

- **CA（证书颁发机构）**：可信第三方为域名签发证书。浏览器/OS 信任库包含约 150 个根 CA
- **证书链**：站点证书 → 中间 CA → 根 CA（必须在浏览器信任库中）
- **证书类型**：DV（域名验证，基本）、OV（组织验证）、EV（扩展验证，曾显示绿条，浏览器已移除）
- **前端开发**：`mkcert` 生成本地受信证书；Let's Encrypt 免费生产证书

#### 开启 HTTPS（前端实践）

**生产环境**：

- nginx/Apache 配置 SSL 证书，强制 HTTPS
- 添加 HSTS 头：`Strict-Transport-Security: max-age=31536000; includeSubDomains; preload`
- HTTP → HTTPS 301 跳转

**本地开发**：

- `mkcert` 生成开发用本地证书
- Vite/CRA 内置 HTTPS 模式

**迁移注意事项**：

- **Mixed Content**：HTTPS 页面的所有嵌入资源也必须 HTTPS。浏览器拦截 active mixed content（script），警告 passive（img）
- CSP 升级：`Content-Security-Policy: upgrade-insecure-requests` 自动将 HTTP 升级为 HTTPS

#### HTTPS 劫持方式与防御

| 攻击           | 原理                               | 防御                                             |
| -------------- | ---------------------------------- | ------------------------------------------------ |
| **MITM 代理**  | 安装自定义 CA 证书，代理在中间解密 | 不要安装不可信 CA 证书                           |
| **证书误签发** | CA 被攻击/疏忽为你域名签发假证书   | 证书透明（Certificate Transparency）公开日志监控 |
| **SSL 剥离**   | 拦截 HTTP 请求阻止升级为 HTTPS     | HSTS preload 列表，浏览器内置强制 HTTPS 名单     |
| **降级攻击**   | 迫使客户端/服务器协商使用弱加密    | 服务端禁用 TLS 1.0/1.1，最低 TLS 1.2，优先 1.3   |

#### HTTPS 调试

- `net::ERR_CERT_AUTHORITY_INVALID` → CA 不受信任（自签名证书）
- `net::ERR_CERT_DATE_INVALID` → 证书过期
- `net::ERR_CERT_COMMON_NAME_INVALID` → 域名不匹配
- Chrome DevTools Security 面板 → 查看证书、加密套件、连接协议

:::

### 2.10 理解WebSocket协议的底层原理、与HTTP的区别

::: details 参考

#### 什么是 WebSocket

全双工、持久的 TCP 连接，允许服务器实时向客户端推送数据，无需客户端轮询。RFC 6455 标准。URI 方案：`ws://`（明文）和 `wss://`（加密，基于 TLS）。

#### HTTP vs WebSocket 对比

| 维度     | HTTP                      | WebSocket              |
| -------- | ------------------------- | ---------------------- |
| 通信方式 | 请求-响应（半双工）       | 全双工双向             |
| 连接状态 | 无状态（Keep-Alive 复用） | 有状态持久连接         |
| 发起方向 | 仅客户端                  | 双方随时发送           |
| 每帧开销 | 500-800 字节 Header       | 2-14 字节              |
| 协议     | 文本                      | 二进制分帧             |
| 适用场景 | 文档传输、REST API        | 实时数据、IM、协作编辑 |

#### 协议升级握手

**客户端请求**（HTTP Upgrade）：

```
GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==       ← 随机 Base64 Nonce
Sec-WebSocket-Version: 13
```

**服务端响应**：

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo= ← SHA-1(key + 魔术GUID)
```

> 魔术 GUID `258EAFA5-E914-47DA-95CA-C5AB0DC85B11` 由 RFC 6455 定义，用于证明服务器真正理解 WebSocket 协议。握手后，同一 TCP 连接变更为 WebSocket 连接。

#### 数据帧结构（简化）

- 字段：FIN（最后一帧）、Opcode（text/binary/ping/pong/close）、MASK（客户端→服务端必须 masking）、Payload 长度、Masking Key（4 字节）、Payload Data
- **Client→Server 掩码**：客户端发的帧与随机 32 位 Key XOR 异或。**防止缓存投毒攻击**——恶意中间代理伪装缓存内容攻击。
- 开销：仅 **2-14 字节/帧** vs HTTP 的 500+ 字节

#### 浏览器端 API

```javascript
const ws = new WebSocket('wss://api.example.com/ws')

ws.onopen = () => {
  ws.send(JSON.stringify({ type: 'subscribe', channel: 'updates' }))
}

ws.onmessage = (event) => {
  const data = JSON.parse(event.data)
  // 处理推送数据
}

ws.onclose = (event) => {
  // code !== 1000 → 异常关闭，需要重连
  if (event.code !== 1000) setTimeout(connect, 3000)
}

ws.onerror = (error) => {
  console.error('WebSocket 错误:', error)
}
```

#### 前端实战关注点

**重连策略**（WebSocket 不会自动重连）：

```javascript
function createWS(url) {
  const ws = new WebSocket(url)
  ws.onclose = (e) => {
    if (e.code !== 1000) {
      const delay = Math.min(1000 * Math.pow(2, attempts), 30000) // 指数退避
      setTimeout(() => createWS(url), delay)
    }
  }
  return ws
}
```

**心跳检测**：浏览器 WebSocket API 不支持 `ping()`，需应用层发送 JSON 心跳消息来检测死连接。

**负载均衡**：WebSocket 是持久 TCP 连接，负载均衡器必须支持 WebSocket（连接升级代理），可能需要粘性会话。

**扩展/替代方案**：

- **SSE（Server-Sent Events）**：仅服务器→客户端，基于 HTTP，自动重连，不支持二进制。适合单向数据推送
- **WebRTC DataChannel**：P2P 连接，UDP 传输，延迟极低。适合音视频通话、P2P 文件共享
- **Socket.io**：WebSocket 的封装库，自动重连、长轮询回退、房间/命名空间。但引入自定义协议开销

:::

## 3 设计模式

### 3.1 熟练使用前端常用的设计模式编写代码，如单例模式、装饰器模式、代理模式等

::: details 参考

#### 单例模式（Singleton）

**目的**：确保一个类只有一个实例，并提供全局访问点。

**前端实例**：

- 全局状态管理器（Redux Store、Pinia Store）
- 弹窗/Toast 管理器——只有一个实例管理弹窗栈
- WebSocket 连接管理器——共享同一连接
- Logger 服务

```javascript
// ES6 Module 本身就是单例——模块只执行一次，导出值被缓存
class WsManager {
  private static instance: WsManager;
  private constructor() {}
  static getInstance() {
    return this.instance ??= new WsManager();
  }
}

// 更简单的方式：直接导出实例
export default new WsManager();
```

> 滥用单例会创建全局可变状态，使测试和 SSR 困难。能用依赖注入时优先 DI。

#### 装饰器模式（Decorator）

**目的**：动态给对象添加行为，不需修改原结构或创建子类。

**前端实例**：

- React HOC（Higher-Order Components）：`connect(mapState)(Component)`、`memo(Component)`
- 中间件模式：Express/Koa/Redux 路由器层层包装
- Vue 指令：`v-loading`、`v-permission` 装饰 DOM 行为
- ES7 Decorators：`@logged`、`@readonly`（配合 class）

```javascript
// 函数装饰器：给任意函数加上日志
function withLogging(fn, name = fn.name) {
  return function (...args) {
    console.time(name)
    const result = fn.apply(this, args)
    console.timeEnd(name)
    return result
  }
}

// React HOC：权限检查装饰器
function withAuth(Component) {
  return function AuthWrapped(props) {
    if (!useAuth().hasPermission) return <Redirect to="/login" />
    return <Component {...props} />
  }
}
```

#### 代理模式（Proxy）

**目的**：提供一个代理/占位来控制对另一个对象的访问。

**前端实例**：

- **Vue 3 响应式系统**：`reactive()` / `ref()` 基于 ES6 `Proxy` 拦截属性读写
- **ES6 `Proxy` 对象**：访问日志、校验、缓存
- **图片懒加载**：代理 img 用占位符 → 滚动到可见区域时替换真实 src
- **API Mock**：拦截 `fetch()` 返回模拟数据
- nginx 反向代理（转发 API 到后端，解决跨域）

```javascript
// ES6 Proxy 实现 API 日志代理
const api = { getUsers: () => fetch('/api/users') }

const apiProxy = new Proxy(api, {
  get(target, prop) {
    console.log(`[API] ${String(prop)} 被调用`)
    return Reflect.get(target, prop, receiver)
  }
})

apiProxy.getUsers() // Log: [API] getUsers 被调用
```

#### 其他常用模式速览

| 模式           | 一句话               | 前端实例                                         |
| -------------- | -------------------- | ------------------------------------------------ |
| **工厂模式**   | 创建对象不指定具体类 | `React.createElement()`、fetch 实例工厂          |
| **策略模式**   | 算法族可互换         | 表单校验策略、支付方式选择                       |
| **模块模式**   | 闭包隐藏私有状态     | ES6 modules、IIFE（历史）                        |
| **适配器模式** | 接口转换             | API 响应 → UI 友好格式、Polyfill                 |
| **组合模式**   | 整体-部分统一接口    | React 组件树、递归表单                           |
| **迭代器模式** | 顺序访问集合         | `for...of`、`[Symbol.iterator]` 实现分页数据迭代 |

:::

### 3.2 发布订阅模式和观察者模式的异同以及实际应用

::: details 参考

#### 两个模式常被混淆，本质区别在于耦合度

#### 观察者模式（Observer Pattern）

- **结构**：Subject（主题）直接维护 Observer（观察者）列表。Subject 知道 Observer 的存在。
- **流程**：Subject 状态变化 → Subject 直接调用每个 Observer 的 `update()` 方法
- **耦合**：**有耦合**——Subject 直接持有 Observer 引用

**前端实例**：

- `MutationObserver`：监听 DOM 变化，直接回调
- `IntersectionObserver`：监听可见性
- Vue 响应式系统：数据的 getter/setter 直接通知 Watcher
- RxJS Observable：`observable.subscribe(observer)`

#### 发布-订阅模式（Pub-Sub Pattern）

- **结构**：Publisher 和 Subscriber 完全解耦，通过事件总线/消息代理（Event Bus/Broker）通信
- **流程**：Publisher → Publish 到 Channel → Broker 发消息给所有订阅该 Channel 的 Subscriber
- **耦合**：**无耦合**——Publisher 不知道谁是 Subscriber，Subscriber 不知道消息来自谁

**前端实例**：

- DOM 事件系统：`addEventListener('click', fn)`，鼠标点击源不知道谁在监听
- Node.js `EventEmitter`：`emitter.on('event', fn)` / `emitter.emit('event', data)`
- Redux：`store.subscribe(listener)` / `store.dispatch(action)`
- `window.postMessage` 跨窗口通信

#### 核心差异表

| 维度     | 观察者模式                       | 发布-订阅模式                          |
| -------- | -------------------------------- | -------------------------------------- |
| 耦合度   | Subject 直接知道 Observer        | 完全解耦，通过 Broker                  |
| 通信方式 | Subject → Observer 直接          | Publisher → Broker → Subscriber        |
| 订阅方   | Observer 注册到 Subject          | Subscriber 注册到 Broker（通过 Topic） |
| 被通知方 | Subject 调用 `observer.update()` | Broker 分发消息                        |
| 类型关系 | 一对多                           | 多对多                                 |

#### 代码对比

**观察者模式**：

```javascript
class Subject {
  constructor() {
    this.observers = []
  }
  subscribe(observer) {
    this.observers.push(observer)
  }
  notify(data) {
    this.observers.forEach((o) => o.update(data))
  }
}

class Observer {
  update(data) {
    console.log('收到:', data)
  }
}

const sub = new Subject()
sub.subscribe(new Observer())
sub.notify('状态变更') // Subject 直接通知 Observer
```

**发布-订阅模式**：

```javascript
class EventBus {
  constructor() {
    this.topics = {}
  }
  subscribe(topic, handler) {
    ;(this.topics[topic] ??= []).push(handler)
  }
  publish(topic, data) {
    ;(this.topics[topic] || []).forEach((fn) => fn(data))
  }
}

const bus = new EventBus()
bus.subscribe('user:login', (data) => console.log('登录:', data))
bus.publish('user:login', { name: 'Tom' }) // 发布者不知道订阅者是谁
```

#### 怎么选

- **观察者**：有清晰的"数据源→依赖方"关系时使用。数据流清晰、易追踪（Vue 响应式、数据绑定、Direct Observer API）
- **发布-订阅**：不相干的模块间需要解耦通信时使用。微前端通信、跨组件事件、插件系统。EventBus 增加了间接层，但也方便了独立开发

> RxJS 的 `Subject` 是两者的桥梁：它既是一个 Observer（可以 subscribe Observable），又是一个 Observable（可以被 subscribe），相当于流式编程中的事件代理。

:::

### 3.3 可以说出几种设计模式在开发中的实际应用，理解框架源码中对设计模式的应用

::: details 参考

#### 各框架中的设计模式

**React**：

- **观察者模式**：`setState` → 组件重新渲染。状态是 Subject，组件是 Observer
- **组合模式**：React 组件树。叶子（普通元素）和组合（容器组件）共享统一接口（render / JSX）
- **工厂模式**：`React.createElement(type, props, children)` 创建 VNode
- **装饰器模式**：HOC（`connect`、`memo`、`withRouter`）
- **责任链模式**：事件冒泡——事件沿组件树上传，每个处理者可消费或传递

**Vue**：

- **代理模式**：Vue 3 的 `reactive()` 基于 ES6 `Proxy`，拦截属性读写实现依赖收集
- **观察者模式**：模板渲染函数是 Effect（观察者），响应式数据是 Subject（被观察者）
- **策略模式**：编译器策略——web 编译与 SSR 编译使用不同编译策略；DOM 操作的不同 Patch 策略
- **装饰器/插件模式**：`Vue.use(plugin)` 为 Vue 实例增加功能
- **管道/中间件模式**：Vue Router 导航守卫（`beforeEach` → `beforeResolve` → `afterEach`）

**Angular**：

- **依赖注入模式**：核心模式——Service 被注入到 Component，不需要手动 import
- **装饰器模式**：`@Component`、`@Injectable`、`@Input`、`@Output` 都是装饰器

**状态管理库**：

- **Flux/Redux**：**命令模式**（Action 是命令对象封装状态变更数据）+ **观察者模式**（`store.subscribe()`）
- **MobX**：**观察者模式**——可观察对象自动追踪观察者，精准更新
- **Zustand**：**单例/模块模式**——Store 是模块级单例，通过选择器订阅

**构建工具**：

- **Babel**：**访问者模式**（Visitor Pattern）——遍历 AST，每个节点类型触发对应回调
- **webpack Loader 链**：**责任链/管道模式**——`style-loader!css-loader!sass-loader` 依次处理
- **webpack Plugin Hooks**：**观察者模式**——`compiler.hooks.done.tap('MyPlugin', callback)`，Tapable 机制
- **webpack Target**：**策略模式**——`target: 'web'` / `'node'` / `'webworker'` 不同输出策略

#### 真实项目中的模式应用

| 模式       | 项目场景                           | 具体做法                                               |
| ---------- | ---------------------------------- | ------------------------------------------------------ |
| **单例**   | 全局 Toast/通知管理                | 确保页面只有一个 Toast 栈                              |
| **策略**   | 支付方式选择（微信/支付宝/信用卡） | 每种支付实现同一接口，动态切换                         |
| **观察者** | 表单校验                           | 每个字段作为观察者，监听 model 变化自动校验            |
| **适配器** | API 数据转换层                     | API 原始响应 → 适配器 → UI 友好格式                    |
| **装饰器** | 权限校验 HOC                       | `withAuth(Component)` 包裹任意组件加权限逻辑           |
| **命令**   | 编辑器撤销/重做                    | 每个编辑操作为一个命令对象，含 `execute()` 和 `undo()` |
| **中介者** | 多步骤表单向导                     | 中介者协调导航、校验、数据收集，步骤间不直接通信       |
| **享元**   | 虚拟滚动                           | 少量 DOM 元素复用为超长列表渲染（DOM 元素池）          |
| **代理**   | 图片懒加载                         | 代理控制 src 替换时机，真图片加载前展示占位符          |
| **迭代器** | 分页 API 数据                      | `[Symbol.iterator]` 实现游标分页的可迭代对象           |

#### 设计模式认知的意义

不需要"为了用模式而用模式"。真正的价值在于：

1. **阅读框架源码**时能理解为什么这么写
2. **与团队沟通**时能简洁描述设计意图
3. **重构时**能识别出应该用什么模式来降低复杂度

> 好的设计模式让代码更简单，而不是更复杂。如果引入一个模式后代码变得更难理解了，那可能用错了或不应该用。

:::
