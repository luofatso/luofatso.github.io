# 前端自检系列 --- 运行环境

[[TOC]]

我们需要理清语言和环境的关系：

> ECMAScript描述了JavaScript语言的语法和基本对象规范

> 浏览器作为JavaScript的一种运行环境，为它提供了：文档对象模型（DOM），描述处理网页内容的方法和接口、浏览器对象模型（BOM），描述与浏览器进行交互的方法和接口

> Node也是JavaScript的一种运行环境，为它提供了操作I/O、网络等API

## 1 浏览器API

### 1.1 浏览器提供的符合W3C标准的DOM操作API、浏览器差异、兼容性

::: details 参考
DOM（Document Object Model）是浏览器将 HTML/XML 文档解析为树形结构的编程接口。W3C 制定了 DOM 标准（DOM Level 1-4），所有现代浏览器都遵循该标准。

#### 核心 DOM 操作 API

**节点查询**

```js
// 通过选择器查询 — 最常用
document.querySelector('.box') // 单个元素，不存在返回 null
document.querySelectorAll('.item') // 静态 NodeList，不会实时更新

// 通过 ID / 类名 / 标签 / name 属性查询
document.getElementById('app') // 最快，返回单个元素
document.getElementsByClassName('item') // 动态 HTMLCollection，DOM 变化实时反映
document.getElementsByTagName('div') // 动态 HTMLCollection
document.getElementsByName('username') // 常用于表单元素
```

**节点创建与修改**

```js
// 创建
const div = document.createElement('div')
const text = document.createTextNode('Hello')
const frag = document.createDocumentFragment()  // 内存中的轻量容器，不触发回流

// 插入
parent.appendChild(child)         // 末尾追加
parent.insertBefore(new, ref)     // 指定位置前插入
parent.append(...nodes)           // 现代 API，支持多个节点 + 字符串
parent.prepend(...nodes)          // 开头插入

// 替换 / 删除
parent.replaceChild(new, old)
parent.removeChild(child)
child.remove()                    // 现代 API，直接移除自身
```

**属性与内容操作**

```js
el.getAttribute('data-id') // 获取 HTML 属性值（字符串）
el.setAttribute('data-id', '123') // 设置 HTML 属性
el.removeAttribute('data-id')

// 类名操作 — 推荐用 classList 而非 className
el.classList.add('active')
el.classList.remove('hidden')
el.classList.toggle('dark')
el.classList.contains('active')

// 内容操作
el.innerHTML = '<span>html</span>' // 解析 HTML，有 XSS 风险
el.textContent = 'text' // 纯文本，安全
el.outerHTML // 包含元素自身的 HTML
```

**尺寸与位置**

```js
el.offsetWidth / el.offsetHeight // border + padding + content（含滚动条）
el.clientWidth / el.clientHeight // padding + content（不含边框和滚动条）
el.scrollWidth / el.scrollHeight // 实际内容尺寸（含溢出部分）
el.getBoundingClientRect() // 相对视口的位置和尺寸，{top, left, bottom, right, width, height}
```

#### 浏览器差异与兼容性

| 场景            | 差异描述                                                  | 解决方案                              |
| --------------- | --------------------------------------------------------- | ------------------------------------- |
| IE 旧版         | 不支持 `querySelectorAll`（IE6-7）                        | 使用 `getElementById` + 降级 polyfill |
| IE 事件模型     | `attachEvent` vs `addEventListener`，`this` 指向 `window` | 统一封装事件函数                      |
| IE 的 innerText | IE 支持，Firefox 早期不支持                               | 使用 `textContent`（标准）或特性检测  |
| Safari          | 部分 CSSOM 特性支持较慢（如 `document.styleSheets` 操作） | 使用 CSS 变量替代直接操作样式表       |
| 移动端          | iOS Safari 对 `scroll` 事件优化不同（passive 的需要）     | 使用 `{passive: true}` 提升滚动性能   |

#### 兼容性最佳实践

1. **特性检测 > 浏览器嗅探**：`if ('querySelector' in document)` 而不是 `if (navigator.userAgent.includes('IE'))`
2. **使用 Babel / PostCSS 做构建时 polyfill**
3. **使用成熟的 DOM 抽象库**（React / Vue / jQuery），它们内部处理了兼容性
4. **现代项目可明确放弃 IE 支持**，参考 `browserslist` 配置
   :::

### 1.2 浏览器提供的浏览器对象模型 (BOM)提供的所有全局API、浏览器差异、兼容性

::: details 参考
BOM（Browser Object Model）是浏览器暴露的、与网页内容无关的宿主对象集合。它没有统一标准，由各浏览器自行实现，但核心 API 已经高度一致。

#### BOM 核心分类

**`window` 对象 — 全局作用域 + 窗口控制**

```js
// 窗口尺寸
window.innerWidth / window.innerHeight // 视口尺寸（含滚动条）
window.outerWidth / window.outerHeight // 浏览器窗口外尺寸

// 打开/关闭窗口
window.open(url, 'target', 'width=500,height=400')
window.close() // 只能关闭自己打开的窗口

// 滚动
window.scrollTo({ top: 0, behavior: 'smooth' })
window.scrollBy({ top: 100, left: 0 })
```

**`location` 对象 — URL 解析与导航**

```js
location.href = 'https://example.com' // 跳转（会产生历史记录）
location.replace('https://example.com') // 替换当前页面（不产生历史）
location.reload() // 刷新页面

// URL 解析
location.protocol // 'https:'
location.hostname // 'example.com'
location.port // '443'
location.pathname // '/path/page'
location.search // '?id=1&name=test'
location.hash // '#section-1'
```

**`history` 对象 — 会话历史管理**

```js
history.back() / history.forward() / history.go(-1)

// History API（SPA 路由基础）
history.pushState({ page: 1 }, '', '/page1') // 新增历史条目
history.replaceState({ page: 2 }, '', '/page2') // 替换当前条目
window.addEventListener('popstate', (e) => {
  console.log(e.state) // pushState 时存入的状态数据
})
```

**`navigator` 对象 — 浏览器与设备信息**

```js
navigator.userAgent // UA 字符串（可伪造，不推荐用于逻辑判断）
navigator.language // 浏览器语言 'zh-CN'
navigator.onLine // 是否联网
navigator.cookieEnabled // Cookie 是否启用
navigator.clipboard // 剪贴板 API（需用户授权）
navigator.geolocation // 地理位置 API（需用户授权）
navigator.mediaDevices // 媒体设备（摄像头/麦克风）
navigator.connection // 网络信息（Chrome）— effectiveType: '4g' / '3g' / '2g'
```

**`screen` 对象 — 屏幕信息**

```js
screen.width / screen.height // 屏幕分辨率
screen.availWidth / screen.availHeight // 可用区域（排除任务栏）
screen.colorDepth // 色深
```

**定时器**

```js
const id1 = setTimeout(() => {}, 1000) // 延迟执行（最小延迟 4ms 嵌套时）
const id2 = setInterval(() => {}, 1000) // 周期执行（注意累积效应）
clearTimeout(id1)
clearInterval(id2)

// 现代替代方案
const id3 = requestAnimationFrame(() => {}) // 与刷新率同步（~16ms），自动暂停
cancelAnimationFrame(id3)
```

**弹窗与对话框**

```js
alert('消息')
confirm('确认?') // 返回 true/false
prompt('输入:') // 返回输入值或 null
```

#### 浏览器差异

| API                    | 差异                                             | 处理方式                                             |
| ---------------------- | ------------------------------------------------ | ---------------------------------------------------- |
| `navigator.userAgent`  | 各浏览器格式不同，且可伪造                       | 不用于功能判断，仅用于统计/日志                      |
| `navigator.connection` | 仅 Chromium 内核支持                             | 使用 Network Information API 时做特性检测            |
| `navigator.clipboard`  | Firefox 只支持 `writeText`，Safari 需用户手势    | 统一用异步 API + 降级 `document.execCommand('copy')` |
| `screen` 属性          | 高分屏下 `width` 返回 CSS 像素还是物理像素不统一 | 使用 `window.devicePixelRatio` 配合计算              |
| `history.pushState`    | iOS 14 之前在某些场景不触发 `popstate`           | SPA 路由库（vue-router / react-router）已内部处理    |

#### 兼容性最佳实践

1. **不在生产代码中依赖 `alert` / `confirm` / `prompt`**，使用自定义 UI 组件替代
2. **剪贴板 API 需要 `navigator.permissions.query()` 先检查权限**
3. **定时器精度受浏览器节流策略影响**（后台标签页最小间隔 1000ms），关键计时使用 `performance.now()` + 修正逻辑
4. **`navigator.onLine` 只表示网络连接，不代表能访问目标服务器**，请求失败才是最终判断依据
   :::

### 1.3 大量DOM操作、海量数据的性能优化(合并操作、Diff、requestAnimationFrame等)

::: details 参考
DOM 操作是前端性能瓶颈的主要来源之一，因为每次 DOM 变更都可能触发样式计算、布局（回流）和绘制。

#### 为什么 DOM 操作昂贵

1. **DOM 是 C++ 实现的独立模块**，JS 引擎与 DOM 之间通过桥接层通信，每次跨层调用都有开销
2. **单次 DOM 修改可能触发连锁反应**：修改一个元素 → 样式重算 → 布局 → 绘制 → 合成，整条渲染流水线重新执行
3. **读写交替会强制同步布局**——浏览器无法批处理，性能急剧下降

#### 核心优化策略

**1. 批量 DOM 操作 — 使用 DocumentFragment 或离线节点**

```js
// ❌ 差：循环中逐个插入，每次都触发回流
list.forEach((item) => {
  const li = document.createElement('li')
  li.textContent = item
  ul.appendChild(li) // N 次回流
})

// ✅ 好：使用 DocumentFragment，一次性插入
const frag = document.createDocumentFragment()
list.forEach((item) => {
  const li = document.createElement('li')
  li.textContent = item
  frag.appendChild(li) // 内存操作，不触发回流
})
ul.appendChild(frag) // 仅 1 次回流

// ✅ 更好：cloneNode 离线操作
const clone = ul.cloneNode(true) // 深拷贝（不复制事件）
// 修改 clone...
ul.parentNode.replaceChild(clone, ul)
```

**2. 避免读写交替 — 强制同步布局问题**

```js
// ❌ 差：写-读-写-读交替，每次读都强制同步布局
divs.forEach((el) => {
  el.style.width = el.offsetWidth + 10 + 'px' // 写后立即读，强制回流
})

// ✅ 好：先批量读，再批量写
const widths = divs.map((el) => el.offsetWidth) // 批量读
widths.forEach((w, i) => {
  divs[i].style.width = w + 10 + 'px' // 批量写
})
```

FastDOM 库正是基于这个原理，将读写操作分别放入队列帧末批量执行。

**3. 使用 CSS class 替代内联样式修改**

```js
// ❌ 差：逐条修改触发多次计算
el.style.width = '100px'
el.style.color = 'red'
el.style.opacity = '0.5'

// ✅ 好：一次 class 切换
el.classList.add('active')
```

**4. requestAnimationFrame — 将更新对齐到渲染帧**

```js
// ❌ 差：动画用 setInterval，与刷新率不同步
setInterval(() => {
  box.style.left = x++ + 'px'
}, 16)

// ✅ 好：rAF 在浏览器准备渲染时执行
function animate() {
  box.style.left = x++ + 'px'
  requestAnimationFrame(animate)
}
requestAnimationFrame(animate)
```

rAF 的优势：

- 自动适配显示器刷新率（60Hz → 16ms，120Hz → 8ms）
- 标签页隐藏时自动暂停，节省资源
- 在帧开始时机执行，给浏览器充足时间渲染

**5. 虚拟列表 — 海量数据渲染**

面对万级以上的列表数据，即便全部渲染到 DOM（无操作），内存和初始解析也扛不住。虚拟列表只渲染可视区域 ± 缓冲区的节点，滚动时回收并复用 DOM。

```
┌─────────────────┐
│  不可见（上）    │  ← 不渲染
├─────────────────┤
│  Item 15        │  ← 可视区域（仅渲染 ~10 个节点）
│  Item 16        │
│  Item 17        │
├─────────────────┤
│  不可见（下）    │  ← 不渲染
└─────────────────┘
```

```js
// 核心原理代码示意
function VirtualList({ items, itemHeight, containerHeight }) {
  const totalHeight = items.length * itemHeight
  const [scrollTop, setScrollTop] = useState(0)

  const startIndex = Math.floor(scrollTop / itemHeight)
  const endIndex = Math.min(startIndex + Math.ceil(containerHeight / itemHeight) + 1, items.length)
  const visibleItems = items.slice(startIndex, endIndex)

  return (
    <div
      style={{ height: containerHeight, overflow: 'auto' }}
      onScroll={(e) => setScrollTop(e.target.scrollTop)}
    >
      <div style={{ height: totalHeight, position: 'relative' }}>
        {visibleItems.map((item, i) => (
          <div
            key={startIndex + i}
            style={{ position: 'absolute', top: (startIndex + i) * itemHeight }}
          >
            {item}
          </div>
        ))}
      </div>
    </div>
  )
}
```

**6. DOM Diff 思想**

框架（React / Vue）在 JS 侧维护虚拟 DOM 树，状态变化时：

1. 生成新虚拟 DOM 树
2. 与旧树进行 Diff（O(n) 复杂度，通过同级比较 + key 优化）
3. 计算出最小 DOM 变更集
4. 一次性提交真实 DOM 更新

关键优化：

- **同层级比较**：只比较同层节点，不跨层（复杂度从 O(n³) 降到 O(n)）
- **key 属性**：帮助识别列表中的节点移动、增删，避免不必要的销毁重建
- **组件级跳过**：`shouldComponentUpdate` / `React.memo` / `computed` 减少 Diff 范围
  :::

### 1.4 浏览器海量数据存储、操作性能优化

::: details 参考
这里讨论的是内存中的数据处理（非持久化存储）。面对海量数据时的优化思路：**减少处理量、减少处理次数、用对数据结构**。

#### 1. Web Worker — 将计算移到后台线程

JS 主线程同时负责渲染和 JS 执行，大量计算会阻塞 UI。将计算移到 Worker 线程，主线程只负责接收结果并渲染。

```js
// main.js
const worker = new Worker('worker.js')
worker.postMessage(rawData) // 发送数据（结构化克隆，大数组开销大）
worker.onmessage = (e) => {
  const result = e.data
  render(result) // 拿到结果直接渲染
}

// worker.js
self.onmessage = (e) => {
  const data = e.data
  const aggregated = data.reduce(/* 复杂聚合 */)
  self.postMessage(aggregated)
}
```

> 大数据传输优化：使用 `postMessage(data, [data.buffer])` 转移所有权（Transferable），避免拷贝开销。

#### 2. 分片处理 — 时间切片 (Time Slicing)

将一个长任务切成多个小块，每块处理完让出主线程给渲染。

```js
// 基于 setTimeout 的时间切片
function processChunk(items, processFn, chunkSize = 100, done) {
  let i = 0
  function chunk() {
    const end = Math.min(i + chunkSize, items.length)
    for (; i < end; i++) processFn(items[i])
    if (i < items.length) {
      setTimeout(chunk, 0) // 让出主线程
    } else {
      done()
    }
  }
  chunk()
}

// 基于 requestIdleCallback（仅在空闲时执行）
function idleProcess(items, processFn, done) {
  let i = 0
  function chunk(deadline) {
    while (i < items.length && deadline.timeRemaining() > 1) {
      processFn(items[i++])
    }
    if (i < items.length) {
      requestIdleCallback(chunk)
    } else {
      done()
    }
  }
  requestIdleCallback(chunk)
}

// React 18+ 的并发模式本质上就是基于这个思路，框架自动处理
```

#### 3. 选用合适的数据结构

| 数据结构      | 适用场景                      | 前端中的实现                         |
| ------------- | ----------------------------- | ------------------------------------ |
| `Map`         | 频繁增删、键非字符串          | `new Map()` — 比对象快，保持插入顺序 |
| `Set`         | 去重、存在性判断              | `new Set([...])` — O(1) 查找         |
| `WeakMap`     | 关联数据但不想阻止 GC         | DOM 节点附加数据                     |
| TypedArray    | 数值密集计算（Canvas、WebGL） | `new Float64Array(n)` — 连续内存     |
| ArrayBuffer   | 二进制数据操作                | 文件分片上传、音视频处理             |
| 前缀树 (Trie) | 搜索提示、路径匹配            | 自行实现或第三方库                   |

```js
// ❌ 差：用数组做频繁查找
const found = list.find((item) => item.id === targetId) // O(n)

// ✅ 好：用 Map 索引
const index = new Map(list.map((item) => [item.id, item]))
const found = index.get(targetId) // O(1)
```

#### 4. 增量计算与缓存

```js
// ❌ 差：每次渲染都重新排序/过滤
const sorted = data.sort((a, b) => a.price - b.price) // O(n log n)

// ✅ 好：数据未变化时使用缓存
let cachedSorted = null
let lastDataRef = null
function getSorted(data) {
  if (data === lastDataRef) return cachedSorted
  lastDataRef = data
  cachedSorted = [...data].sort((a, b) => a.price - b.price)
  return cachedSorted
}
```

框架中的实践：

- `useMemo` / `computed`：依赖不变则跳过计算
- `React.memo`：props 不变则跳过组件渲染
- MobX / Vue 的响应式系统：自动追踪依赖，只重算受影响的部分

#### 5. 服务端侧 — 计算下推到后端

前端适合展示和交互，海量数据的聚合、搜索、排序应尽量在服务端完成：

```js
// 前端只请求当前页需要的数据
const { data, total } = await fetch(`/api/list?page=${page}&size=20&sort=price&keyword=${kw}`)
// 百万行数据的排序/过滤/分组由数据库（MySQL / ES）在服务端完成
```

:::

### 1.5 DOM事件流的具体实现机制、不同浏览器的差异、事件代理

::: details 参考
DOM 事件流描述了事件在 DOM 树中传播的完整路径，分为三个阶段：**捕获阶段 → 目标阶段 → 冒泡阶段**。

#### 三阶段模型

```
                  ┌─────────┐
                  │  window │
                  └────┬────┘
              捕获 ↓  │  ↑ 冒泡
                  ┌────┴────┐
                  │ document│
                  └────┬────┘
              捕获 ↓  │  ↑ 冒泡
                  ┌────┴────┐
                  │  <html> │
                  └────┬────┘
              捕获 ↓  │  ↑ 冒泡
                  ┌────┴────┐
                  │  <body> │
                  └────┬────┘
              捕获 ↓  │  ↑ 冒泡
                  ┌────┴────┐
                  │  <div>  │ ← 目标阶段（到达事件源）
                  └─────────┘
```

1. **捕获阶段（Capture）**：事件从 `window` → `document` → ... → 目标元素的父级
2. **目标阶段（Target）**：事件到达目标元素本身
3. **冒泡阶段（Bubble）**：事件从目标元素 → ... → `window`（与捕获路径相反）

```js
// 默认在冒泡阶段触发
button.addEventListener('click', handler) // 冒泡阶段
button.addEventListener('click', handler, true) // 捕获阶段
button.addEventListener('click', handler, { capture: true }) // 等价写法
```

#### 事件对象关键属性

```js
element.addEventListener('click', (e) => {
  e.target // 触发事件的源元素（点击的最深层元素）
  e.currentTarget // 绑定监听器的元素（即这里的 element）
  e.eventPhase // 1=捕获, 2=目标, 3=冒泡
  e.type // 事件类型 'click'
  e.preventDefault() // 阻止默认行为（链接跳转、表单提交）
  e.stopPropagation() // 阻止事件继续传播（捕获+冒泡）
  e.stopImmediatePropagation() // 阻止传播 + 阻止同一元素上其他同类监听器
})
```

#### 事件委托（事件代理）

利用事件冒泡机制，将子元素的监听器统一绑定到父级上，通过 `e.target` 判断实际触发源。

```js
// ❌ 差：N 个子元素绑定 N 个监听器
items.forEach((item) => {
  item.addEventListener('click', handleClick)
})

// ✅ 好：事件委托 — 父级统一处理
list.addEventListener('click', (e) => {
  const item = e.target.closest('.item') // 向上匹配最近的 .item
  if (!item) return // 点击的不是 .item，忽略
  const id = item.dataset.id
  handleClick(id)
})
```

优势：

- 减少监听器数量 → 降低内存
- 动态增删子元素无需手动绑定/解绑
- 代码结构更清晰

注意事项：

- `focus`、`blur`、`scroll`、`mouseenter`、`mouseleave` **不冒泡**（要用 `focusin` / `focusout` 替代）
- `e.target` 可能被深层子元素干扰，推荐使用 `e.target.closest(selector)` 向上匹配
- React 17+ 将所有事件委托到 `root` 节点，React 16 委托到 `document`

#### 浏览器差异

| 时代     | 模型          | 特点                                           |
| -------- | ------------- | ---------------------------------------------- |
| Netscape | 捕获模型      | 事件从外到内                                   |
| IE       | 冒泡模型      | 事件从内到外                                   |
| W3C 标准 | 先捕获后冒泡  | `addEventListener` 第三个参数控制阶段          |
| IE8-     | `attachEvent` | 无捕获阶段，`this` 指向 `window`（非触发元素） |

现代浏览器已全部遵循 W3C 标准，不再需要关注 `attachEvent`。
:::

### 1.6 前端发起网络请求的几种方式及其底层实现、可以手写原生ajax、fetch、可以熟练使用第三方库

::: details 参考

#### 方式总览

| 方式                     | 底层             | 特点                                         | 适用场景                     |
| ------------------------ | ---------------- | -------------------------------------------- | ---------------------------- |
| `XMLHttpRequest`         | 浏览器 HTTP 引擎 | 支持进度、取消、超时，API 繁琐               | 需要进度回调、兼容老浏览器   |
| `fetch`                  | Fetch API        | Promise 风格，简洁，流式读取                 | 现代浏览器默认选择           |
| `navigator.sendBeacon`   | HTTP POST        | 不阻塞页面卸载，不阻塞页面卸载               | 埋点上报、页面关闭前发送数据 |
| `<script>` JSONP         | HTTP GET         | 跨域兼容性好（利用 `<script>` 不受同源限制） | 历史遗留，不推荐新使用       |
| WebSocket                | TCP 升级         | 全双工、长连接、低延迟                       | 实时通信（聊天、行情推送）   |
| Server-Sent Events (SSE) | HTTP 长连接      | 服务端单向推送，自动重连                     | 日志推送、消息通知           |

#### 手写 XMLHttpRequest

```js
function ajax({ url, method = 'GET', data = null, headers = {}, timeout = 5000 }) {
  return new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest()
    xhr.open(method, url)

    // 设置请求头
    Object.entries(headers).forEach(([k, v]) => xhr.setRequestHeader(k, v))

    xhr.timeout = timeout

    xhr.onload = () => {
      if ((xhr.status >= 200 && xhr.status < 300) || xhr.status === 304) {
        resolve(JSON.parse(xhr.responseText))
      } else {
        reject(new Error(`HTTP ${xhr.status}`))
      }
    }

    xhr.onerror = () => reject(new Error('Network error'))
    xhr.ontimeout = () => reject(new Error(`Timeout: ${timeout}ms`))
    xhr.onprogress = (e) => console.log(`Loaded: ${e.loaded} / ${e.total}`) // 上传下载进度
    xhr.upload.onprogress = (e) => {} // 上传进度

    xhr.send(data)
  })
}
```

#### 手写 fetch 封装

```js
async function request(url, options = {}) {
  const { timeout = 10000, ...fetchOptions } = options

  const controller = new AbortController()
  const timer = setTimeout(() => controller.abort(), timeout)

  try {
    const res = await fetch(url, {
      ...fetchOptions,
      signal: controller.signal,
      headers: {
        'Content-Type': 'application/json',
        ...fetchOptions.headers
      },
      body: fetchOptions.body ? JSON.stringify(fetchOptions.body) : undefined
    })
    clearTimeout(timer)

    if (!res.ok) throw new Error(`HTTP ${res.status}: ${res.statusText}`)
    const data = await res.json()
    return data
  } catch (err) {
    clearTimeout(timer)
    if (err.name === 'AbortError') throw new Error(`Timeout: ${timeout}ms`)
    throw err
  }
}
```

> `fetch` 的坑：**只有网络错误或请求被取消才 reject**，HTTP 4xx/5xx 仍然 resolve。需手动检查 `res.ok`。

#### fetch vs XHR 本质差异

| 维度     | XHR                                     | fetch                                       |
| -------- | --------------------------------------- | ------------------------------------------- |
| 错误处理 | HTTP 错误也 resolve，需手动判断         | 仅网络错误 reject                           |
| 超时     | 原生 `xhr.timeout` 属性                 | 需配合 `AbortController` 手动实现           |
| 进度     | 支持 `onprogress` / `upload.onprogress` | 不支持（可用 `ReadableStream` 间接实现）    |
| 取消     | `xhr.abort()`                           | `AbortController.abort()`                   |
| Cookie   | 默认携带同源 Cookie                     | 默认不携带，需设置 `credentials: 'include'` |
| 流式读取 | 不支持                                  | `response.body.getReader()` 支持            |

#### 第三方库

- **Axios**：最流行的 HTTP 库，拦截器、自动 JSON 转换、请求/响应转换
- **TanStack Query (React Query) / SWR**：服务端状态管理，缓存、去重、重试、乐观更新
- **ky**：基于 fetch 的轻量库，语法更简洁
- **ofetch**：unjs 出品，跨平台（Node + 浏览器）统一 fetch 接口
  :::

### 1.7 浏览器的同源策略，如何避免同源策略，几种方式的异同点以及如何选型

::: details 参考
同源策略（Same-Origin Policy）是浏览器最核心的安全机制：**协议、域名、端口**三者完全相同才算同源，任一不同即构成跨域。

| 对比     | URL A               | URL B                | 是否同源 | 原因               |
| -------- | ------------------- | -------------------- | -------- | ------------------ |
| 同源     | `https://a.com/p1`  | `https://a.com/p2`   | ✅       | 协议+域名+端口一致 |
| 协议不同 | `https://a.com`     | `http://a.com`       | ❌       | 协议不同           |
| 子域名   | `https://a.com`     | `https://www.a.com`  | ❌       | 域名不同           |
| 端口     | `https://a.com:443` | `https://a.com:8443` | ❌       | 443 ≠ 8443         |

同源策略**限制的不是请求的发出**（请求照样能到达服务器），而是浏览器**禁止 JS 读取跨域响应**。

#### 跨域方案对比

| 方案            | 原理                                     | 限制                   | 适用场景                                  |
| --------------- | ---------------------------------------- | ---------------------- | ----------------------------------------- |
| **CORS**        | 服务器响应头 `Access-Control-Allow-*`    | 需服务端配合           | **首选方案，生产环境标准**                |
| JSONP           | 动态 `<script>` 标签加载，回调函数传数据 | 仅 GET，只支持 JS 响应 | 历史遗留，不推荐                          |
| 代理（Proxy）   | 同源服务器中转请求                       | 需额外服务器           | 开发环境常用（webpack-dev-server / vite） |
| WebSocket       | ws://协议不受同源策略限制                | 需服务端支持 WebSocket | 实时双向通信                              |
| postMessage     | `window.postMessage` 跨窗口通讯          | 需对方窗口配合监听     | iframe / 跨标签通信                       |
| Nginx 反向代理  | 将不同服务路径映射到同一域名             | 需运维配合             | 生产环境合一部署                          |
| document.domain | 设置相同主域，使子域可以通信             | 仅限同主域，已废弃     | 不应该再使用                              |

#### CORS 详解（首选方案）

```http
# 服务器响应头
Access-Control-Allow-Origin: https://foo.example        # 或 *
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: X-Custom-Header, Content-Type
Access-Control-Allow-Credentials: true                   # 允许携带 Cookie
Access-Control-Max-Age: 86400                            # 预检缓存时间(秒)
```

**简单请求 vs 预检请求（Preflight）**

- **简单请求**（同时满足）：方法为 GET/HEAD/POST、Content-Type 为 `text/plain` / `multipart/form-data` / `application/x-www-form-urlencoded`、无自定义头部 → 直接发送，浏览器自动检查响应头
- **预检请求**：不满足上述任一条件 → 先发 `OPTIONS` 请求询问服务器是否允许，通过后再发实际请求

```js
// 会触发预检的常见操作
fetch('https://api.example.com/data', {
  method: 'PUT', // 非简单方法
  headers: { 'Content-Type': 'application/json' }, // 非简单 Content-Type
  body: JSON.stringify({ name: 'hi' })
})
```

#### JSONP 原理（仅作了解）

```js
// 客户端
function jsonp(url) {
  return new Promise((resolve) => {
    const callback = 'jsonp_' + Date.now()
    const script = document.createElement('script')
    script.src = `${url}?callback=${callback}`
    window[callback] = (data) => {
      resolve(data)
      document.head.removeChild(script)
      delete window[callback]
    }
    document.head.appendChild(script)
  })
}

// 服务端返回
// callback({ name: 'hi' })   // 实际是一段可执行 JS
```

#### 选型建议

1. **首选 CORS**：服务端可控时，响应头配置一步到位
2. **开发环境用 Proxy**：Vite 的 `server.proxy` 或 webpack 的 `devServer.proxy`
3. **无法改服务端又必须跨域**：Nginx 反向代理统一域名
4. **实时通信**：WebSocket
5. **跨窗口/iframe 通讯**：postMessage
   :::

### 1.8 浏览器提供的几种存储机制、优缺点、开发中正确的选择

::: details 参考

#### 五种存储机制对比

| 特性           | Cookie         | sessionStorage   | localStorage         | IndexedDB                | Cache API        |
| -------------- | -------------- | ---------------- | -------------------- | ------------------------ | ---------------- |
| **容量**       | ~4KB           | 5-10MB           | 5-10MB               | 浏览器限额（可达数百MB） | 浏览器限额       |
| **生命周期**   | 可设置过期时间 | 标签页关闭即清除 | 永久（除非手动删除） | 永久                     | 需手动管理       |
| **作用域**     | 同源 + 同路径  | 同源 + 同标签    | 同源                 | 同源                     | 同源             |
| **随请求发送** | ✅ 自动携带    | ❌               | ❌                   | ❌                       | ❌               |
| **数据类型**   | 字符串         | 字符串           | 字符串               | 任意类型（结构化克隆）   | Request/Response |
| **异步**       | ❌ 同步        | ❌ 同步          | ❌ 同步              | ✅ 异步                  | ✅ 异步          |
| **适用量级**   | 极少量         | 少量             | 少量 ~ 中等          | 大量                     | HTTP 缓存        |

#### Cookie 详解

```js
// 设置
document.cookie = 'token=abc123; max-age=3600; path=/; domain=.example.com; secure; samesite=lax'

// 读取（只能拿到 key=value，拿不到属性）
console.log(document.cookie) // 'token=abc123; theme=dark'

// 服务端设置
// Set-Cookie: sessionId=xyz; HttpOnly; Secure; SameSite=Strict
```

关键属性：

- `HttpOnly`：禁止 JS 访问，防御 XSS 窃取 Cookie
- `Secure`：仅 HTTPS 传输
- `SameSite`：`Strict`（跨站不发） / `Lax`（允许顶层导航 GET） / `None`（总是发送，需配合 Secure）

> Cookie 的最大问题：**每次 HTTP 请求自动携带**，即使用不上也会增加请求体积。这也是为什么 JWT 方案更倾向于用 `Authorization` 头部 + localStorage 而非 Cookie。

#### IndexedDB — 大型结构化数据的唯一选择

```js
// 打开数据库
const dbReq = indexedDB.open('myDB', 1)
dbReq.onupgradeneeded = (e) => {
  const db = e.target.result
  const store = db.createObjectStore('users', { keyPath: 'id' })
  store.createIndex('name', 'name', { unique: false })
}

// 写入
const tx = db.transaction('users', 'readwrite')
tx.objectStore('users').put({ id: 1, name: 'Alice' })

// 查询（异步，不会卡主线程）
tx.objectStore('users').get(1).onsuccess = (e) => console.log(e.target.result)
```

#### 存储选型决策树

```
需要随 HTTP 请求发送? ──是──→ Cookie（HttpOnly + Secure + SameSite）
    │
   否
    │
   数据量 > 5MB? ──是──→ IndexedDB
    │
   否
    │
   需要跨标签共享? ──否──→ sessionStorage（敏感临时数据，如表单进度）
    │
   是（需要永久保留）
    │
    └──→ localStorage（主题设置、token 等）
```

#### 安全注意

| 机制         | 风险                 | 防护                                   |
| ------------ | -------------------- | -------------------------------------- |
| localStorage | XSS 可直接读取 token | 避免存敏感 token，优先 HttpOnly Cookie |
| Cookie       | CSRF 攻击            | SameSite + CSRF Token                  |
| IndexedDB    | XSS 可读写           | 内容加密（Web Crypto API）             |
| 所有存储     | 浏览器扩展/恶意脚本  | 敏感数据不落盘或加密                   |

:::

### 1.9 浏览器跨标签通信

::: details 参考
同一浏览器中，不同标签页/窗口（同源）之间需要进行数据通信的场景：一个标签页登录后通知其他标签页刷新、多标签页数据同步等。

#### 方案对比

| 方案                            | 通信方向             | 实时性 | 复杂度 | 适用场景             |
| ------------------------------- | -------------------- | ------ | ------ | -------------------- |
| **BroadcastChannel**            | 广播（同源所有标签） | 实时   | 极低   | **首选**，同源广播   |
| **localStorage + storage 事件** | 广播（仅非触发页）   | 实时   | 低     | 数据同步             |
| **SharedWorker**                | 多对一               | 实时   | 高     | 复杂共享状态         |
| **postMessage**                 | 点对点（父子窗口）   | 实时   | 低     | window.open / iframe |
| **Service Worker**              | 一对多               | 实时   | 高     | PWA 推送、缓存同步   |
| **Cookie 轮询**                 | 广播                 | 延迟   | 低     | 兼容极端场景         |

#### 1. BroadcastChannel（推荐首选）

API 极其简洁，同源页面间广播消息：

```js
// 标签页 A
const channel = new BroadcastChannel('app-sync')
channel.postMessage({ type: 'login', user: 'Alice' })

// 标签页 B（同源下的其他所有标签页）
const channel = new BroadcastChannel('app-sync')
channel.onmessage = (e) => {
  if (e.data.type === 'login') {
    console.log(`${e.data.user} 在其他标签页登录`)
  }
}

// 关闭通道
channel.close()
```

#### 2. localStorage + storage 事件

利用 `storage` 事件只在**其他标签页**触发（不在当前页触发）的特性：

```js
// 标签页 A：写入 localStorage
localStorage.setItem('sync_key', JSON.stringify({ action: 'logout', ts: Date.now() }))

// 标签页 B：监听 storage 变化
window.addEventListener('storage', (e) => {
  if (e.key === 'sync_key') {
    const data = JSON.parse(e.newValue)
    if (data.action === 'logout') {
      location.href = '/login'
    }
  }
})
```

局限：需要在写入时多写一个时间戳或随机值，否则相同值不会触发事件。

#### 3. postMessage — 父子窗口/iframe 通信

```js
// 父页面
const childWin = window.open('https://sub.example.com/page')
childWin.postMessage({ type: 'update', payload }, 'https://sub.example.com')

window.addEventListener('message', (e) => {
  if (e.origin !== 'https://sub.example.com') return // 始终验证 origin
  console.log('收到:', e.data)
})

// 子页面
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://parent.example.com') return
  window.opener?.postMessage({ status: 'ok' }, 'https://parent.example.com')
  // window.parent.postMessage(...) // 与 iframe 父级通信
})
```

#### 4. SharedWorker — 多标签共享一个 Worker

```js
// shared-worker.js
let ports = []
self.onconnect = (e) => {
  const port = e.ports[0]
  ports.push(port)
  port.onmessage = (msg) => {
    ports.forEach((p) => p !== port && p.postMessage(msg.data))
  }
  port.start()
}
```

#### 选型建议

- **简单广播** → BroadcastChannel（API 最简洁）
- **需要兼容老浏览器** → localStorage + storage 事件
- **父子窗口通讯** → postMessage
- **多标签共享一个复杂状态对象** → SharedWorker
- **PWA / 后台推送** → Service Worker
  :::

## 2 浏览器原理

### 2.1 各浏览器使用的JavaScript引擎以及它们的异同点、如何在代码中进行区分

::: details 参考

#### 主流 JS 引擎

| 引擎                     | 所属浏览器                             | 开发商    | 首次发布 | 特点                                                                         |
| ------------------------ | -------------------------------------- | --------- | -------- | ---------------------------------------------------------------------------- |
| **V8**                   | Chrome / Edge / Opera / Node.js / Deno | Google    | 2008     | JIT 编译，Ignition(解释器) + TurboFan(优化编译)，隐藏类                      |
| **SpiderMonkey**         | Firefox                                | Mozilla   | 1996     | 最早的 JS 引擎，JIT + IonMonkey 优化编译器                                   |
| **JavaScriptCore (JSC)** | Safari                                 | Apple     | 2008     | 原名 SquirrelFish Extreme，四层 JIT 编译管线（LLInt → Baseline → DFG → FTL） |
| **Chakra**               | IE / 旧 Edge                           | Microsoft | 2011     | 已废弃，Edge 已切换至 V8                                                     |
| **Hermes**               | React Native                           | Meta      | 2019     | 专为移动端设计，AOT 编译，启动快，内存占用低                                 |

#### 核心差异

| 维度        | V8                                | SpiderMonkey              | JavaScriptCore                   |
| ----------- | --------------------------------- | ------------------------- | -------------------------------- |
| 解释器      | Ignition                          | 基于 Baseline Interpreter | LLInt (Low Level Interpreter)    |
| 优化编译器  | TurboFan (之前 Crankshaft)        | Warp → IonMonkey          | Baseline JIT → DFG JIT → FTL JIT |
| GC          | Orinoco（并行、并发、增量）       | 分代 + 压缩               | 分代 + 并发标记                  |
| 内联缓存    | 通过隐藏类 (Hidden Classes / Map) | Shape / ObjectGroup       | Structure / StructureID          |
| WebAssembly | Liftoff (基线) + TurboFan         | Cranelift (即将) + Ion    | BBQ + OMG                        |

#### 如何在代码中区分

```js
// 不推荐的 UA 检测
navigator.userAgent.includes('Chrome')

// 推荐的特性检测
function detectEngine() {
  // V8 特有：Error 对象的 stack 格式
  try {
    throw new Error()
  } catch (e) {
    const stack = e.stack || ''
    if (stack.includes('at ')) return 'V8' // Chrome/Edge/Node
    if (stack.includes('@')) return 'SpiderMonkey' // Firefox
  }

  // JSC 特有：Function 的 displayName 支持
  // 以及 WebKit 特有的 CSS 属性
  if (CSS.supports('-webkit-touch-callout', 'none')) {
    return 'JavaScriptCore' // Safari
  }
}
```

> **核心原则**：永远不要依赖 UA 或引擎差异来做业务逻辑——浏览器厂商可能改变任何内部行为。需要特定能力时，使用**特性检测**（Feature Detection），如 `if ('CSS' in window && CSS.supports('...'))`。
> :::

### 2.2 请求数据到请求结束与服务器进行了几次交互

::: details 参考
这个问题核心考察的是 **TCP 连接建立和关闭**的次数，以及 **HTTP 版本差异**。

#### 最短交互场景：一次完整的 HTTP/1.1 请求

```
客户端                        服务器
   │                            │
   │ ──── SYN ───────────────→ │
   │ ←─── SYN + ACK ───────── │   } TCP 三次握手（建立连接）
   │ ──── ACK ───────────────→ │
   │                            │
   │ ──── HTTP Request ──────→ │   } HTTP 请求响应
   │ ←─── HTTP Response ───── │
   │                            │
   │ ──── FIN ───────────────→ │
   │ ←─── ACK ─────────────── │
   │ ←─── FIN ─────────────── │   } TCP 四次挥手（关闭连接）
   │ ──── ACK ───────────────→ │
```

**总计：3 + 2 + 4 = 9 次交互**（包含三次握手、请求/响应、四次挥手。实际上挥手可能合并 ACK，最少约 7 次交互包）

#### HTTP/1.1 持久连接（Keep-Alive）

HTTP/1.1 默认启用 `Connection: keep-alive`，连接不会立即关闭，可以复用：

```
TCP 三次握手 → 请求1 → 响应1 → 请求2 → 响应2 → ... → 四次挥手
```

**首次 3 次握手后，后续请求省去了连接开销**。对同一域名的多个请求显著减少总交互次数。

#### HTTPS（TLS 握手额外开销）

HTTPS 在 TCP 三次握手后还需 TLS 握手：

```
TCP 三次握手 (3次)
   +
TLS 1.2 握手 (4次: ClientHello → ServerHello → Certificate → Finished)
   +
HTTP 请求/响应 (2次)
   +
TCP 四次挥手 (4次)
────────────────────────
= 约 13 次交互（首次连接，不含复用）
```

TLS 1.3 将握手精简为 2 次（1-RTT），总交互约 11 次。会话恢复（Session Resumption / 0-RTT）甚至可以将 TLS 部分缩减为 0 次。

#### HTTP/2 和 HTTP/3

| 版本     | 传输层     | 连接数              | 特点                           |
| -------- | ---------- | ------------------- | ------------------------------ |
| HTTP/1.1 | TCP        | 同一域名 6-8 个连接 | 每个连接串行处理请求           |
| HTTP/2   | TCP        | 同域名 1 个连接     | 多路复用，一个连接并发所有请求 |
| HTTP/3   | QUIC (UDP) | 同域名 1 个连接     | 0-RTT 握手，无队头阻塞         |

HTTP/2 多路复用意味着：对同一服务器的所有请求只需 **1 次 TCP + 1 次 TLS 握手**，极大减少了交互次数。

#### DevTools 视角

Chrome Network 面板的 Timing：

```
Queueing        → 请求在队列中等待的时间
Stalled         → 等待可用 TCP 连接的时间
DNS Lookup      → DNS 查询（1 次 UDP 往返）
Initial connection → TCP 握手 + TLS 握手
Request sent    → 发送请求数据
Waiting (TTFB)  → 服务器处理 + 响应第一个字节到达
Content download → 下载响应内容
```

> 首次请求的 `Initial connection` 时间本质就是 3 次 TCP + 2~4 次 TLS 交互的总和。
> :::

### 2.3 可详细描述浏览器从输入URL到页面展现的详细过程

::: details 参考
这是一个经典的综合题，考察对整个 Web 技术栈的理解。以下按时间顺序逐步展开：

#### 阶段一：URL 输入 → 网络请求

1. **URL 解析**：浏览器判断输入是 URL 还是搜索关键词，是合法 URL 则解析出协议、域名、端口、路径等
2. **HSTS 预加载列表检查**：若域名在 HSTS 列表中，强制使用 HTTPS（即便用户输入的是 `http://`）
3. **浏览器缓存检查**：依次检查 Service Worker Cache → HTTP 缓存（强缓存 `Expires/Cache-Control`）— 命中则直接返回，跳过后续网络步骤
4. **DNS 解析**（缓存未命中时）：浏览器 DNS 缓存 → OS hosts 文件 → 路由器缓存 → ISP DNS 服务器 → 递归查询根域名服务器 → 顶级域 → 权威 DNS
5. **建立连接**：TCP 三次握手 → （HTTPS 则）TLS 握手
6. **发送 HTTP 请求**：构造请求行/头部/体，通过 TCP 发送

#### 阶段二：服务端处理 → 响应返回

7. **服务端处理**：Web 服务器（Nginx/Apache）接收请求 → 转发给应用服务器 → 路由匹配 → 业务逻辑 → 查询数据库/缓存 → 生成响应
8. **响应返回**：HTTP 状态码 + 响应头 + 响应体（HTML 文档）返回给浏览器
9. **连接处理**：`Connection: keep-alive` 则保留连接；否则四次挥手关闭

#### 阶段三：浏览器解析渲染（关键渲染路径）

10. **解析 HTML 构建 DOM 树**：字节 → 字符 → Token → 节点 → DOM 树。遇到 `<script>` 阻塞解析（除非 `async/defer`），遇到 `<link>` 异步加载 CSS 但会阻塞渲染（不阻塞 DOM 解析）
11. **解析 CSS 构建 CSSOM 树**：CSS 规则从右向左匹配，构建样式规则树
12. **构建 Render 树**：DOM + CSSOM → 只包含可见元素的渲染树（`display: none` 和 `<head>` 不在其中）
13. **布局（Layout / Reflow）**：计算每个节点的几何位置和大小
14. **绘制（Paint）**：将渲染树绘制为图层上的像素
15. **合成（Composite）**：GPU 将各图层合成最终显示的画面

#### 阶段四：页面加载完成

16. **DOMContentLoaded**：DOM 树构建完成，`defer` 脚本在此执行
17. **load**：所有资源（图片、CSS、JS、字体等）加载完毕
18. **后续**：异步资源继续加载，用户交互响应，SPA 路由切换等

#### 完整时序图

```
用户输入URL
    │
    ▼
DNS 解析 (递归查询)
    │
    ▼
TCP 三次握手 ─── (HTTPS?) ─── TLS 握手
    │
    ▼
发送 HTTP 请求 ───────────── 服务端处理
    │
    ▼
接收响应 (HTML 开始到达)
    │
    ├─→ 解析 HTML
    │     ├─→ 构建 DOM 树
    │     └─→ 遇到 <link> ─→ 下载 CSS ─→ 构建 CSSOM
    │     └─→ 遇到 <script> ─→ 下载 + 执行（阻塞 DOM 解析）
    │
    ▼
DOMContentLoaded (DOM + CSSOM 就绪)
    │
    ▼
布局 → 绘制 → 合成 → 首屏展示
    │
    ▼
load (所有资源就绪)
```

#### 性能优化切入点（在此流程中的位置）

| 阶段      | 优化手段                                                         |
| --------- | ---------------------------------------------------------------- |
| DNS       | DNS 预解析 `<link rel="dns-prefetch">`                           |
| 连接      | 预连接 `<link rel="preconnect">`                                 |
| 请求      | HTTP/2 多路复用、减少请求数量、CDN 就近访问                      |
| 缓存      | 强缓存 `Cache-Control: max-age`、协商缓存 `ETag`、Service Worker |
| HTML 解析 | 关键资源内联、延迟非关键 JS（`defer`/`async`）                   |
| CSS 解析  | 关键 CSS 内联、移除未使用 CSS                                    |
| 布局      | 避免强制同步布局、使用 `contain` CSS 属性限制布局范围            |
| 绘制      | 使用 `will-change` / `transform` 提升到合成层                    |

:::

### 2.4 浏览器解析HTML代码的原理，以及构建DOM树的流程

::: details 参考

#### 解析流程：字节 → DOM 树

```
字节 (Bytes)
    │  ↓ 编码解码（根据 Content-Type charset 或 <meta charset>）
字符 (Characters)
    │  ↓ 词法分析 (Tokenizer)
Token (标签)
    │  ↓ 语法分析 (Tree Builder)
节点 (Nodes)
    │  ↓ 树构建
DOM 树
```

#### 详细步骤

**1. 字节解码**：浏览器从网络或磁盘读取 HTML 文件的原始字节，根据编码（HTTP 头的 `Content-Type: text/html; charset=utf-8` 或 `<meta charset="utf-8">`）将字节转为字符。

> 编码检测优先级：HTTP Content-Type 头 > `<meta charset>` > BOM > 浏览器推断

**2. 词法分析（Tokenization）**：将字符流切分为 Token。

```html
<!-- 源码 -->
<div class="box">Hello</div>

<!-- 对应的 Token 流 -->
StartTag: div (attrs: class="box") Character: H, e, l, l, o EndTag: div
```

HTML 的词法分析是**状态机**驱动的。状态机根据当前状态和下一个字符决定输出什么 Token、是否需要切换状态。

**3. 语法分析与树构建**：树构建器（Tree Builder）接收 Token 流，按照 HTML 规范定义的解析规则，将 Token 插入 DOM 树对应位置。

#### 核心机制：容错解析

HTML 最显著的特点是**容错性极强**——浏览器永远不会因为 HTML 不合法而报错崩溃：

```html
<!-- 浏览器能正确解析以下混乱内容 -->
<p>Hello
<li>Item 1
<li>Item 2
<div><span>text</div>  <!-- 标签未闭合，浏览器自动补全 -->
```

浏览器内部维护大量纠错规则（如 "自动闭合"、 "正确嵌套"、 "表格元素的 foster parenting" 等），确保无论如何都能产生一棵可用的 DOM 树。

#### 脚本与 CSS 对 DOM 解析的影响

```
HTML 解析器正在工作...
    │
    ├─→ 遇到 <script src="..."> (无 async/defer)
    │   └─→ ⚠️ 暂停 DOM 解析
    │       └─→ 下载 JS 文件
    │           └─→ 等待前面的 CSS 加载完（CSS 阻塞 JS 执行）
    │               └─→ 执行 JS
    │                   └─→ 恢复 DOM 解析
    │
    ├─→ 遇到 <script async src="...">
    │   └─→ 不阻塞解析，下载完立即执行（顺序不确定）
    │
    ├─→ 遇到 <script defer src="...">
    │   └─→ 不阻塞解析，并行下载，DOM 解析完后按顺序执行
    │
    └─→ 遇到 <link rel="stylesheet">
        └─→ 不阻塞 DOM 解析，但阻塞渲染 + 阻塞后续 <script> 执行
```

关键共识：

- **`<script>`（无属性）阻塞 DOM 解析**
- **CSS 加载不阻塞 DOM 解析，但阻塞渲染和 JS 执行**
- **`defer` 和 `async` 各解决不同场景**：defer 保证顺序，async 追求速度
  :::

### 2.5 浏览器如何解析CSS规则，并将其应用到DOM树上

::: details 参考

#### CSS 解析流程

```
CSS 文本
    │  ↓ 词法分析
Token 流（选择器、属性、值、{、}、:、; 等）
    │  ↓ 语法分析
CSSOM 树（CSS Object Model，结构化样式规则）
    │  ↓ 与 DOM 结合
Render 树（仅包含可见元素）
```

#### CSSOM 的结构

```css
body {
  font-size: 16px;
}
h1 {
  color: red;
  font-size: 2em;
}
p {
  margin: 0;
}
```

```
CSSStyleSheet
├── CSSRule (body)
│   ├── selector: "body"
│   └── style: { font-size: 16px }
├── CSSRule (h1)
│   ├── selector: "h1"
│   └── style: { color: red; font-size: 2em }
└── CSSRule (p)
    └── style: { margin: 0 }
```

#### 选择器匹配：从右向左

浏览器在匹配 CSS 选择器时，采用的是**从右向左**的匹配策略，而非直觉的从左向右：

```css
#content .box p span {
  color: blue;
}
```

```
从左向右（直觉）：找到 #content → 在其中找 .box → 在其中找 p → 在其中找 span ❌ 效率低
从右向左（实际）：找到所有 span → 检查是否有祖先 p → 检查是否有祖先 .box → 检查是否有祖先 #content ✅
```

从右向左的优势：在遍历 DOM 时，最右侧的关键选择器（key selector）通常能快速过滤掉大量不匹配的元素，极大减少不必要的祖先链遍历。

#### 样式计算（Style Computation）

CSSOM 构建完成后，浏览器需要为 DOM 树中的每个节点计算最终样式。这个过程分两步：

**1. 属性值计算**

```
浏览器默认样式 (User Agent Stylesheet)
    ↓
用户自定义样式 (User Stylesheet)
    ↓
开发者样式 (Author Stylesheet) ← 就是我们写的 CSS
    ↓
层叠 (Cascade) — 按 !important > 特异性 > 源码顺序 决策
    ↓
继承 — 某些属性（color, font-family 等）从父级继承
    ↓
初始值 — 未设置且不继承的属性使用默认值
```

**2. 特异度（Specificity）计算**

| 选择器                          | 计算方式 (a,b,c,d) | 特异值 |
| ------------------------------- | ------------------ | ------ |
| `!important`                    | 最高优先级         | ∞      |
| 内联 `style=""`                 | (1,0,0,0)          | 1000   |
| `#id`                           | (0,1,0,0)          | 100    |
| `.class` / `[attr]` / `:pseudo` | (0,0,1,0)          | 10     |
| `div` / `::before`              | (0,0,0,1)          | 1      |
| `*` / 组合器 / `:where()`       | (0,0,0,0)          | 0      |

```css
#nav .item a:hover   /* 0,1,2,1 = 121 */
.content a           /* 0,0,1,1 = 11  */
a                    /* 0,0,0,1 = 1   */
```

**层叠层（Cascade Layers `@layer`）**：CSS 2022 新增，允许控制样式表的优先级顺序，像 z-index 一样排列样式层：

```css
@layer reset, base, components, overrides;

@layer overrides {
  .button {
    background: blue;
  }
}
@layer components {
  .button {
    background: red;
  } /* 即使后面定义，优先级低于 overrides */
}
```

CSS 引擎（如 V8 的 CSS 解析模块 / Firefox 的 Stylo）在引擎内使用哈希表将选择器映射到声明，最终为每个 DOM 节点输出一个 `ComputedStyle` 对象（你可以在 DevTools 的 Computed 面板中看到）。
:::

### 2.6 浏览器如何将解析好的带有样式的DOM树进行绘制

::: details 参考
Render 树构建完成后，浏览器进入**像素化（Pixel Pipeline）**流程，将抽象的树结构转换为屏幕上的像素。

#### 渲染流水线五大步骤

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│  Layout  │ → │  Paint   │ → │  Layer   │ → │ Rasterize│ → │ Composite│
│  布局    │   │  绘制    │   │  分层    │   │  光栅化  │   │   合成   │
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
```

#### 1. Layout 布局（Reflow）

计算每个节点的**几何信息**：在视口中的位置 (x, y) 和尺寸 (width, height)。

```js
// 触发 Layout 的操作
el.offsetWidth // 读几何属性
el.style.width = '100px' // 改样式
el.classList.add('show') // 改变 display
window.getComputedStyle(el) // 获取计算样式
```

布局是一个代价高昂的过程，因为它可能需要遍历整棵树。现代浏览器通过脏标记系统（dirty flag）尽可能只重新计算受影响的子树。

#### 2. Paint 绘制

将每个元素转换为**绘制指令的列表**。每个元素分解成一系列绘制操作（画背景 → 画边框 → 画文字）。

```
绘制 canvas button 的指令序列：
  1. drawRect(0, 0, 100, 40, color='#4A90D9')      // 背景
  2. drawRect(0, 0, 100, 40, border=2, color='#3A7BC8') // 边框
  3. drawText('Click Me', x=50, y=20, font='...')   // 文字
```

#### 3. Layer 分层

浏览器将页面分解为**多个合成图层（Composite Layers）**。特定的元素会被提升到独立的合成层：

触发独立图层的条件：

- 根元素 (`<html>`)
- `position: fixed` 或 `position: sticky`
- 3D transform: `transform: translateZ(0)` 或 `transform: translate3d(0,0,0)`
- `<video>`, `<canvas>`, `<iframe>`
- CSS `will-change: transform` / `will-change: opacity`
- CSS `filter` / `backdrop-filter`
- 有动画/过渡的 `transform` 或 `opacity`

可以通过 DevTools → Rendering → Layer borders 查看图层边界（橙色边框）。

#### 4. Rasterize 光栅化

将每个图层的绘制指令转换为**位图（Bitmap）**。光栅化发生在 GPU 光栅化线程上，主线程不参与。

> Chrome 的分块（Tiling）策略：将大图层切成小方块（tile），按需光栅化，优先处理视口和附近的 tile。

#### 5. Composite 合成

GPU 将各图层位图按 z-index 顺序叠加合并，输出最终屏幕画面。合成在 **Compositor 线程**上完成，完全独立于主线程。

#### 为什么 transform 和 opacity 动画流畅

```
触发 Layout 的动画（如 left/top/width）：
  Layout → Paint → Composite   ← 主线程参与，可能卡顿

仅触发 Composite 的动画（transform / opacity）：
  Composite                    ← 仅在合成线程，不需要主线程
```

这就是为什么高性能动画只推荐用 `transform` 和 `opacity`——它们不需要 Layout 和 Paint，直接在合成线程上完成。

#### 渲染流程图（按变更类型）

```
JS / CSS 变更
    │
    ├─→ 改 geometry (width, left, margin...) → Layout → Paint → Composite
    ├─→ 改 paint only (color, background...) → Paint → Composite  (跳过 Layout)
    └─→ 改 composite only (transform, opacity, cursor...) → Composite  (跳过 Layout + Paint)
```

:::

### 2.7 浏览器的运行机制，如何配置资源异步同步加载

::: details 参考

#### 浏览器进程架构

现代浏览器（以 Chrome 为例）采用**多进程架构**，将不同职责划分到独立进程中：

| 进程             | 职责                                 | 一个 / 多个                           |
| ---------------- | ------------------------------------ | ------------------------------------- |
| **浏览器主进程** | 窗口管理、地址栏、前进后退、文件存储 | 1 个                                  |
| **GPU 进程**     | 3D 绘制、页面合成                    | 1 个                                  |
| **网络进程**     | 所有网络请求                         | 1 个                                  |
| **渲染进程**     | 解析 HTML/CSS/JS、布局、绘制 ⭐      | 每个标签页 1 个（站点隔离下可能多个） |
| **插件进程**     | Flash/PDF 等插件                     | 按需                                  |

每个渲染进程中包含的关键线程：

```
渲染进程
  ├── 主线程 (Main Thread)
  │   ├── JS 引擎 (V8)
  │   ├── HTML 解析器
  │   ├── CSS 解析器
  │   ├── 样式计算
  │   ├── 布局 (Layout)
  │   ├── 绘制 (Paint)
  │   └── 事件循环 (Event Loop)
  ├── 合成线程 (Compositor Thread)
  │   └── 图层合成
  ├── 光栅化线程池 (Raster Threads)
  └── Worker 线程 (Web Workers)
```

#### 为什么 JS 会阻塞页面渲染

主线程是**单线程**运行的。JS 执行、HTML 解析、样式计算、布局、绘制都运行在主线程上。当 JS 正在执行时，渲染的所有步骤都被阻塞。

这就是长任务（Long Task > 50ms）问题的根源——一次长 JS 执行 = 一次渲染帧丢失。

#### 资源加载策略

| 方式                     | 阻塞 DOM 解析 | 执行时机                                    | 适用场景                        |
| ------------------------ | ------------- | ------------------------------------------- | ------------------------------- |
| `<script src>`           | ✅ 是         | 立即执行                                    | 需要控制执行时机的关键脚本      |
| `<script async>`         | ❌ 否         | 下载完立即执行（无序）                      | 独立脚本（统计、广告）          |
| `<script defer>`         | ❌ 否         | DOM 解析完后、`DOMContentLoaded` 前按序执行 | 需要 DOM 但不需要立即执行的脚本 |
| `<script type="module">` | ❌ 否         | 类似 `defer`                                | ES Module                       |
| `<link rel="preload">`   | ❌ 否         | 不执行，仅提前下载                          | 关键资源（字体、首屏 CSS）      |
| `<link rel="prefetch">`  | ❌ 否         | 空闲时下载                                  | 下一页可能用到的资源            |

```html
<!-- defer：并行下载，DOMContentLoaded 前按顺序执行 -->
<script defer src="lib.js"></script>
<script defer src="app.js"></script>
<!-- lib 先执行，再执行 app -->

<!-- async：并行下载，下载完立刻执行，不保证顺序 -->
<script async src="analytics.js"></script>
<script async src="ad.js"></script>
<!-- 哪个先下载完哪个先执行 -->

<!-- module：默认 defer 行为 -->
<script type="module" src="app.js"></script>
```

#### 渲染流程中关键事件顺序

```
开始解析 HTML
    │
    ├─→ <link> CSS 异步下载（不阻塞解析）
    ├─→ <script defer> 异步下载（不阻塞解析）
    ├─→ <script async> 异步下载（不阻塞解析）
    ├─→ <script>（普通）阻塞解析 + 等待 CSSOM → 执行 → 恢复解析
    │
    ▼
DOM 树构建完成 ★
    │
    ├─→ 执行 <script defer> 脚本
    │
    ▼
DOMContentLoaded 事件 ★★
    │
    ├─→ 图片/CSS/字体等资源继续加载
    │
    ▼
所有资源加载完成
    │
    ▼
load 事件 ★★★
```

#### `<link>` 的预加载提示

```html
<!-- DNS 预解析 -->
<link rel="dns-prefetch" href="//api.example.com" />

<!-- TCP + TLS 预连接 -->

```

### 2.8 浏览器回流与重绘的底层原理，引发原因，如何有效避免

::: details 参考

#### 定义

- **回流（Reflow / Layout）**：当元素的几何属性（位置、尺寸）发生变化时，浏览器需要重新计算布局。回流影响整个渲染流水线。
- **重绘（Repaint）**：当元素的外观（颜色、背景、阴影等）变化但不影响布局时，浏览器跳过布局直接重新绘制。

```
回流 = Layout + Paint + Composite  （大开销）
重绘 = Paint + Composite           （中等开销）
仅合成 = Composite                  （最小开销）
```

#### 引发回流的操作

**几何属性改变**：

```js
el.style.width = '100px'
el.style.height = '200px'
el.style.padding = '10px'
el.style.margin = '20px'
el.style.left = '10px'
el.style.top = '20px'
el.style.display = 'none' // 或 block
el.style.border = '1px solid'
el.style.fontSize = '20px'
```

**读写几何属性（强制同步布局）**：

```js
// 以下属性在获取时，如果前面有未提交的样式修改，会强制触发回流
el.offsetTop / el.offsetLeft / el.offsetWidth / el.offsetHeight
el.scrollTop / el.scrollLeft / el.scrollWidth / el.scrollHeight
el.clientTop / el.clientLeft / el.clientWidth / el.clientHeight
el.getClientRects()
el.getBoundingClientRect()
window.getComputedStyle(el)
```

**DOM 结构变更**：

```js
document.body.appendChild(newDiv) // 新增元素
parent.removeChild(child) // 删除元素
el.innerHTML = '...' // 内容变更
```

**浏览器窗口缩放、字体大小变更、`:hover` 伪类激活等**

#### 引发重绘的操作

```js
el.style.color = 'red'
el.style.backgroundColor = 'blue'
el.style.borderColor = 'green'
el.style.boxShadow = '0 0 5px'
el.style.outline = '1px solid'
el.style.visibility = 'hidden' // visibility 触发重绘但 display: none 触发回流
```

#### 优化策略

**1. 使用 CSS class 批量修改**

```js
// ❌ 差：每条都触发回流
el.style.width = '100px'
el.style.padding = '10px'
el.style.border = '1px solid'

// ✅ 好：一次 class 切换
el.classList.add('expanded')
```

**2. 读写分离**

```js
// ❌ 差：写后立即读，触发强制同步布局
el.style.width = el.offsetWidth + 10 + 'px'

// ✅ 好：先批量读，再批量写
const widths = els.map((e) => e.offsetWidth)
els.forEach((e, i) => (e.style.width = widths[i] + 10 + 'px'))
```

**3. 离线 DOM 操作**

```js
// ❌ 差：在实时 DOM 上循环修改
items.forEach((item) => {
  const li = document.createElement('li')
  li.textContent = item
  ul.appendChild(li) // 每次触发回流
})

// ✅ 好：在 DocumentFragment 或 cloneNode 上操作
const frag = document.createDocumentFragment()
items.forEach((item) => {
  const li = document.createElement('li')
  li.textContent = item
  frag.appendChild(li)
})
ul.appendChild(frag) // 一次性回流

// ✅ 或者：先 display: none（从 Render 树移除），修改完再显示
el.style.display = 'none'
// ... 大量 DOM 操作 ...
el.style.display = 'block' // 仅 2 次回流
```

**4. 将动画限制在合成层**

```css
/* ❌ 差：left 触发 Layout */
.box {
  transition: left 0.3s;
}

/* ✅ 好：transform 仅在合成线程 */
.box {
  transition: transform 0.3s;
  will-change: transform;
}
```

**5. CSS `contain` 属性 — 明确告诉浏览器布局边界**

```css
.widget {
  contain: layout; /* 此元素的布局变化不影响外部，外部变化也不影响它 */
}
.widget {
  contain: strict; /* 且不依赖 CSS 计数器/引号 */
}

/* 等价于 */
content-visibility: auto; /* 视口外元素自动跳过渲染，大幅提升长页面性能 */
```

**6. 用 `requestAnimationFrame` 操纵读/写时机**

```js
// 读取在帧开始
const pos = el.getBoundingClientRect()
// 写入合并到帧结束
requestAnimationFrame(() => {
  el.style.transform = `translateY(${pos.top}px)`
})
```

### 2.9 浏览器的垃圾回收机制，如何避免内存泄漏

::: details 参考
JavaScript 的内存管理是**自动的**（GC = Garbage Collection），但理解其机制对写出高性能、无泄漏的代码至关重要。

#### 内存生命周期

```
分配 (Allocate) → 使用 (Use) → 释放 (Release)
                                    ↑ GC 负责
```

#### V8 的分代垃圾回收

V8 将堆内存分为两代：**新生代**（Young Generation）和**老生代**（Old Generation）。

|              | 新生代 (Young)              | 老生代 (Old)              |
| ------------ | --------------------------- | ------------------------- |
| **大小**     | 1-8 MB                      | 较大，按需增长            |
| **对象特征** | 新创建的、寿命短            | 经过两次 GC 存活、体积大  |
| **GC 算法**  | Scavenge（Cheney 复制算法） | Mark-Sweep + Mark-Compact |
| **频率**     | 频繁（几十ms 一次）         | 较低                      |
| **暂停时间** | 极短                        | 较长（全堆扫描）          |

#### 新生代 GC: Scavenge 算法

```
From 空间（活跃）    →    To 空间（空闲）
    │                          │
    ├─→ 标记存活对象 ─────────→ 复制到 To 空间
    │                           │
    └─→ 剩余（死亡）对象直接丢弃   │
                                │
                    交换From和To ←┘
```

优点：只处理存活对象（死亡的不碰），速度快。
缺点：一半空间闲置（复制需要空闲空间）。

经过两次 Scavenge 仍存活的对象被**晋升（Promote）**到老生代。

#### 老生代 GC: Mark-Sweep + Mark-Compact

**标记-清除 (Mark-Sweep)**：

1. 从根对象（全局对象、调用栈）出发，遍历所有引用
2. **可达 = 存活**，不可达 = 垃圾
3. 清除不可达对象

**标记-压缩 (Mark-Compact)**：
当内存碎片化严重时，将存活对象向一端移动，避免碎片导致的分配失败。

#### V8 的 GC 优化手段

| 优化             | 说明                                        |
| ---------------- | ------------------------------------------- |
| **并行 GC**      | 主线程 + 多个辅助线程同时工作               |
| **增量标记**     | GC 分小块执行，与 JS 交替进行，减少单次暂停 |
| **并发标记**     | 标记阶段在后台线程与 JS 同时运行（不阻塞）  |
| **惰性清除**     | 清除阶段按需进行，不一次性全清              |
| **Orinoco 项目** | V8 GC 的代号，集成了上述所有优化            |

#### 常见内存泄漏场景

**1. 意外的全局变量**

```js
// ❌ 泄漏
function foo() {
  bar = 'leak' // 未声明 → 挂到 window 上，永远不回收
  this.name = 'leak' // 非严格模式下 this = window
}

// ✅ 修复
;('use strict') // 或其他严格模式检查
```

**2. 遗忘的定时器 / 回调**

```js
// ❌ 泄漏：组件销毁了但定时器还在
useEffect(() => {
  const id = setInterval(() => {
    /* 持有组件引用 */
  }, 1000)
  // 忘记 clearInterval
}, [])

// ✅ 修复：清理
useEffect(() => {
  const id = setInterval(() => {
    /* ... */
  }, 1000)
  return () => clearInterval(id)
}, [])
```

**3. 游离的 DOM 引用**

```js
// ❌ 泄漏
const elements = {
  button: document.getElementById('myBtn') // JS 持有引用
}
document.body.removeChild(document.getElementById('myBtn')) // DOM 节点删了，但 elements.button 还引用着 → 不会 GC

// ✅ 修复
elements.button = null // 解除引用
```

**4. 闭包引用了不需要的大对象**

```js
// ❌ 泄漏：闭包持有整个 largeData，即使只用了一小部分
function outer() {
  const largeData = new Array(1000000) // 大对象
  return function inner() {
    return largeData[0] // 只用了第一个元素，但整个数组都无法回收
  }
}

// ✅ 修复：只保留需要的
function outer() {
  const largeData = new Array(1000000)
  const first = largeData[0]
  return function inner() {
    return first // 仅 first 被闭包引用，largeData 可以被 GC
  }
}
```

**5. 事件监听器未解绑**

```js
// ❌ 泄漏：元素被移除但监听器还在
el.addEventListener('click', handler)
el.remove()

// ✅ 修复：使用 removeEventListener（或在现代框架中自动处理）
el.removeEventListener('click', handler)
```

- **Chrome DevTools → Memory → Heap Snapshot**：拍快照对比内存差异
- **Chrome DevTools → Performance → Memory 复选框**：时间线看内存增长趋势
- **`performance.memory`**：`{ usedJSHeapSize, totalJSHeapSize, jsHeapSizeLimit }`（仅 Chrome）

### 2.10 浏览器采用的缓存方案，如何选择和控制合适的缓存方案

::: details 参考
浏览器缓存体系是多层次的，从请求到最终展示，每一层都有对应的缓存机制。

#### 缓存层次全景

```
┌──────────────────────────────────────────┐
│          Service Worker Cache            │  ← JS 完全控制
├──────────────────────────────────────────┤
│          HTTP 缓存（浏览器内置）          │
│  ┌──────────────┐  ┌──────────────────┐  │
│  │  强缓存       │  │   协商缓存        │  │
│  │  (强缓存过期   │  │   (304 Not       │  │
│  │   后走协商)    │  │    Modified)      │  │
│  └──────────────┘  └──────────────────┘  │
├──────────────────────────────────────────┤
│          HTTP/2 Push Cache               │  ← 服务端主动推送
├──────────────────────────────────────────┤
│     内存缓存 (Memory Cache / Blink)      │  ← 页面关闭即清
├──────────────────────────────────────────┤
│   磁盘缓存 (Disk Cache / HTTP Cache)      │  ← 持久化
├──────────────────────────────────────────┤
│          CDN / 代理服务器缓存             │  ← 中间层
└──────────────────────────────────────────┘
```

#### 一、HTTP 强缓存（无需发请求）

服务端通过响应头告知浏览器：在此有效期内直接用缓存，不发网络请求。

```http
# HTTP/1.0 — 绝对时间
Expires: Wed, 01 Jan 2025 00:00:00 GMT

# HTTP/1.1 — 相对时间（优先级高于 Expires）
Cache-Control: max-age=3600          # 3600 秒内有效
Cache-Control: max-age=31536000, immutable  # 一年，且资源内容不可变
Cache-Control: no-cache              # 可缓存但每次必须协商验证
Cache-Control: no-store              # 完全不缓存
Cache-Control: public                # 可被 CDN/代理缓存
Cache-Control: private               # 仅浏览器缓存，CDN 不缓存
Cache-Control: must-revalidate       # 过期后必须重新验证
```

**`max-age` vs `Expires`**：max-age 使用相对时间，不受客户端时间影响；Expires 是绝对时间，客户端时钟不准会导致问题。

**`immutable`**：告诉浏览器资源永不变化，即使按 F5 刷新也不发验证请求。适用于带 hash 的文件（`app.abc123.js`），省去一次 304 往返。

#### 二、HTTP 协商缓存（需发请求验证）

强缓存过期后，浏览器携带验证信息向服务端确认资源是否有变化。未变化则返回 `304 Not Modified`（无 body），浏览器使用本地缓存。

```http
# 方案 A：时间戳验证
# 请求头
If-Modified-Since: Wed, 01 Jan 2025 00:00:00 GMT
# 响应头（无变化）
Last-Modified: Wed, 01 Jan 2025 00:00:00 GMT
HTTP 304 Not Modified

# 方案 B：内容指纹验证（更可靠）
# 请求头
If-None-Match: "abc123"
# 响应头（无变化）
ETag: "abc123"
HTTP 304 Not Modified
```

| 方案   | 头字段                                | 精度   | 缺点                                              |
| ------ | ------------------------------------- | ------ | ------------------------------------------------- |
| 时间戳 | `Last-Modified` / `If-Modified-Since` | 秒级   | 1 秒内多次修改检测不到；文件内容不变但 mtime 变化 |
| 指纹   | `ETag` / `If-None-Match`              | 内容级 | 计算 ETag 有少量服务端开销                        |

#### 三、Service Worker Cache

Service Worker 运行在浏览器后台的独立线程，可以拦截所有网络请求并自由决定是走网络还是走缓存。这就是 PWA 离线可用的基础。

```js
// sw.js
const CACHE_NAME = 'v1'

// 安装时预缓存关键资源
self.addEventListener('install', (e) => {
  e.waitUntil(
    caches
      .open(CACHE_NAME)
      .then((cache) => cache.addAll(['/', '/styles/main.css', '/scripts/app.js']))
  )
})

// 拦截请求：缓存优先策略
self.addEventListener('fetch', (e) => {
  e.respondWith(caches.match(e.request).then((cached) => cached || fetch(e.request)))
})
```

SW 缓存策略：

- **Cache First**：先查缓存，没有才发网络（适合静态资源）
- **Network First**：先发网络，失败才用缓存（适合 API）
- **Stale While Revalidate**：立即返回缓存，同时后台更新缓存（适合平衡体验和新鲜度）
- **Network Only / Cache Only**

#### 四、Memory Cache vs Disk Cache

|              | Memory Cache                                      | Disk Cache          |
| ------------ | ------------------------------------------------- | ------------------- |
| **速度**     | 极快（内存读写）                                  | 较慢（磁盘 I/O）    |
| **生命周期** | 进程级，标签页关闭即清                            | 持久化，按 LRU 淘汰 |
| **容量**     | 较小                                              | 较大（可达数百 MB） |
| **典型用途** | 当前页面内重复请求                                | 跨页面、跨会话复用  |
| **查看**     | DevTools → Network → Size 列显示 `(memory cache)` | `(disk cache)`      |

浏览器自动决定放内存还是磁盘（一般规则：小文件、频繁访问 → 内存；大文件、不频繁 → 磁盘）。

#### 五、前端缓存策略实践

**资源文件名 Hash（长缓存 + 失效）**

```
app.abc123.js    → max-age=31536000, immutable  （永久缓存）
app.def456.js    → 内容变了 hash 变了，新请求拿新文件
```

Webpack 的 `[contenthash]` 和 Vite 的 hash 都是这个原理。

**HTML 不使用强缓存**

```http
# index.html — 每次都必须验证（或短期缓存）
Cache-Control: no-cache  # 或 max-age=0
```

因为 HTML 是资源的入口，它引用变化后的 JS/CSS 文件名，所以 HTML 必须保持新鲜。

**选型决策表**

| 资源类型             | 缓存策略                 | 典型 max-age               |
| -------------------- | ------------------------ | -------------------------- |
| HTML 入口文件        | 协商缓存（或短期强缓存） | 0 ~ 5 分钟                 |
| JS/CSS（带 hash）    | 强缓存 + immutable       | 1 年                       |
| 图片/字体（带 hash） | 强缓存 + immutable       | 1 年                       |
| API 响应             | 不缓存 / 短期 + 协商     | `no-cache` 或 `max-age=10` |
| 用户头像/Logo        | 短期强缓存               | 1 小时 ~ 1 天              |
| CDN 资源             | 强缓存 + CDN 刷新机制    | 1 年                       |

### 3.2 掌握一种Node开发框架，如Express，Express和Koa的区别

::: details 参考

#### Express

Express 是 Node.js 最经典的 Web 框架（2010），采用**中间件洋葱模型**，API 基于回调风格。

```js
const express = require('express')
const app = express()

// 中间件
app.use(express.json())
app.use((req, res, next) => {
  console.log(`${req.method} ${req.url}`)
  next()
})

// 路由
app.get('/api/users/:id', async (req, res) => {
  const user = await getUser(req.params.id)
  res.json(user)
})

// 错误处理中间件（4参数签名）
app.use((err, req, res, next) => {
  res.status(500).json({ error: err.message })
})

app.listen(3000)
```

#### Koa

Koa 是 Express 原班人马打造的新一代框架（2015），基于 `async/await`，不内置任何中间件。

```js
const Koa = require('koa')
const Router = require('@koa/router')

const app = new Koa()
const router = new Router()

// 中间件
app.use(async (ctx, next) => {
  const start = Date.now()
  await next()
  console.log(`${ctx.method} ${ctx.url} - ${Date.now() - start}ms`)
})

// 路由
router.get('/api/users/:id', async (ctx) => {
  ctx.body = await getUser(ctx.params.id)
})

app.use(router.routes())
app.listen(3000)
```

#### 核心差异

| 维度           | Express                                        | Koa                                     |
| -------------- | ---------------------------------------------- | --------------------------------------- |
| **异步模型**   | 回调 (`req, res, next`)                        | async/await (`ctx, next`)               |
| **中间件执行** | 线性：`next()` 后代码在响应后才执行            | 洋葱：`await next()` 前后都能执行代码   |
| **内置功能**   | 路由、静态文件、模板引擎                       | **零内置**，全部需要中间件              |
| **Response**   | `res.send()` / `res.json()` / `res.sendFile()` | `ctx.body = ...`，统一赋值              |
| **Request**    | `req.body`（需 body-parser）                   | `ctx.request.body`（需 koa-bodyparser） |
| **错误处理**   | 4 参数中间件 `(err, req, res, next)`           | `try/catch` 或 `ctx.onerror`            |
| **生态**       | 庞大成熟，中间件极丰富                         | 较新，中间件需找 koa-\* 版本            |
| **体积**       | 较大                                           | 极简核 + 按需安装                       |

#### 洋葱模型的本质

```
       Request →
    ┌──────────────────────┐
    │   中间件 1            │
    │  ┌──────────────────┐│
    │  │  中间件 2         ││
    │  │ ┌───────────────┐││
    │  │ │  中间件 3      │││
    │  │ │  核心逻辑      │││
    │  │ └───────────────┘││
    │  └──────────────────┘│
    └──────────────────────┘
       Response ←
```

Express 也能实现洋葱效果但需要手动控制；Koa 的 `async/await` 实现洋葱模型更自然。

```js
// Koa 洋葱模型示例
app.use(async (ctx, next) => {
  console.log('1. 进入 A')
  await next() // ★ 在这里暂停，等所有下游中间件执行完
  console.log('5. 离开 A') // 响应返回前最后执行的代码
})
app.use(async (ctx, next) => {
  console.log('2. 进入 B')
  await next()
  console.log('4. 离开 B')
})
app.use(async (ctx) => {
  console.log('3. 核心逻辑')
  ctx.body = 'done'
})
// 输出顺序：1 → 2 → 3 → 4 → 5
```

#### 选型建议

- **中小型 API / 微服务** → Koa（简洁、现代）
- **需要大量现成中间件 / 快速原型** → Express（生态大）
- **全栈框架 / SSR** → Next.js / Nuxt / Nest.js
- **追求极致性能** → Fastify（benchmark 远超 Express 和 Koa）

#### path — 路径处理

path 模块解决跨平台路径问题（Windows 用 `\`，Unix 用 `/`）。

```js
const path = require('path')

path.join('/foo', 'bar', 'baz/asdf') // '/foo/bar/baz/asdf' — 智能拼接
path.resolve('/foo', './bar') // '/foo/bar' — 解析为绝对路径
path.resolve('src', 'index.js') // '/current/work/dir/src/index.js'

path.dirname('/foo/bar/baz.txt') // '/foo/bar'
path.basename('/foo/bar/baz.txt') // 'baz.txt'
path.extname('/foo/bar/baz.txt') // '.txt'

path.parse('/foo/bar/baz.txt')
// { root: '/', dir: '/foo/bar', base: 'baz.txt', ext: '.txt', name: 'baz' }

path.relative('/data/orandea/test/aaa', '/data/orandea/impl/bbb')
// '../../impl/bbb'
```

> `path.join` vs `path.resolve`：join 是纯拼接；resolve 会解析成绝对路径（从当前工作目录出发）。

#### http — 创建 HTTP 服务器

```js
const http = require('http')

const server = http.createServer((req, res) => {
  // req: IncomingMessage (Readable Stream)
  const { method, url, headers } = req

  let body = ''
  req.on('data', (chunk) => (body += chunk))
  req.on('end', () => {
    // res: ServerResponse (Writable Stream)
    res.writeHead(200, { 'Content-Type': 'application/json' })
    res.end(JSON.stringify({ url, method }))
  })
})

server.listen(3000, () => console.log('Listening on :3000'))
```

底层原理：`http.createServer` 底层调用 `net.createServer`（TCP 服务器），收到 TCP 连接后将字节流解析为 HTTP 报文（请求行 → 头部 → 体），最终构造成 `req`/`res` 对象。

#### child_process — 子进程管理

```js
const { exec, execFile, spawn, fork } = require('child_process')

// exec — 执行 shell 命令，返回完整输出（适合短小命令）
exec('ls -la', (err, stdout, stderr) => {
  console.log(stdout)
})

// spawn — 流式输出，适合长时间/大量输出的命令
const child = spawn('git', ['log', '--oneline'])
child.stdout.pipe(process.stdout)
child.stderr.on('data', (chunk) => console.error(chunk.toString()))
child.on('close', (code) => console.log(`退出码: ${code}`))

// fork — 创建 Node 子进程，自带 IPC 通道
// parent.js
const worker = fork('./worker.js')
worker.send({ task: 'process', data: largeArray })
worker.on('message', (result) => console.log(result))

// worker.js
process.on('message', ({ data }) => {
  const result = heavyCompute(data)
  process.send(result)
})
```

| API        | 用途                 | 通信                   | 是否 Node |
| ---------- | -------------------- | ---------------------- | --------- |
| `exec`     | 简单 shell 命令      | 回调 stdout/stderr     | 否        |
| `execFile` | 执行可执行文件       | 回调                   | 否        |
| `spawn`    | 长时间进程、流式 I/O | Stream                 | 否        |
| `fork`     | 创建 Node 子进程     | IPC (`send`/`message`) | 是        |

### 3.4 Node的底层运行原理、和浏览器的异同

::: details 参考

#### Node 的架构层级

```
┌────────────────────────────────────┐
│        JavaScript 代码（用户代码）    │  ← 你写的
├────────────────────────────────────┤
│      Node.js Core API（JS 层）      │  ← fs / http / path / buffer ...
├────────────────────────────────────┤
│   Node.js C++ Bindings（绑定层）    │  ← node_file.cc / node_http.cc ...
├────────────────────────────────────┤
│         libuv（事件循环）            │  ← ★ Node 异步 I/O 的核心
├────────────────────────────────────┤
│       V8（JS 引擎）+ C-ares + ...  │
├────────────────────────────────────┤
│         操作系统 (OS)               │
└────────────────────────────────────┘
```

**libuv** 是 Node 异步能力的核心——一个跨平台的 C 库，抽象了操作系统的异步 I/O 机制：

- Linux: epoll
- macOS: kqueue
- Windows: IOCP

#### Node 的事件循环（Event Loop）

与浏览器不同，Node 的事件循环分为 **6 个阶段**，每个阶段有一个 FIFO 回调队列：

```
   ┌────────────────────────────┐
┌─→│        timers              │  setTimeout / setInterval 回调
│  └─────────────┬──────────────┘
│  ┌─────────────┴──────────────┐
│  │   pending callbacks        │  系统操作回调（如 TCP 错误）
│  └─────────────┬──────────────┘
│  ┌─────────────┴──────────────┐
│  │   idle / prepare           │  内部使用
│  └─────────────┬──────────────┘
│  ┌─────────────┴──────────────┐
│  │       poll                 │  ★ 最重要的阶段：
│  │                            │    - 接收新的 I/O 事件
│  │                            │    - 执行 I/O 回调（除 timers/close）
│  └─────────────┬──────────────┘
│  ┌─────────────┴──────────────┐
│  │       check                │  setImmediate 回调
│  └─────────────┬──────────────┘
│  ┌─────────────┴──────────────┐
│  │   close callbacks          │  socket.on('close', ...)
│  └─────────────┬──────────────┘
│                │
└────────────────┘
```

`process.nextTick()` 和 `Promise.then()` 不属于事件循环的 6 个阶段，它们属于**微任务**，在每个阶段切换之间执行：

```js
setTimeout(() => console.log('A'), 0)
setImmediate(() => console.log('B'))
process.nextTick(() => console.log('C'))
Promise.resolve().then(() => console.log('D'))

// 输出：C → D → A → B （或 C → D → B → A，取决于主模块加载时机）
// nextTick 和 Promise 在事件循环阶段切换时先执行
```

#### Node vs 浏览器 对比

| 维度               | 浏览器                                      | Node                                      |
| ------------------ | ------------------------------------------- | ----------------------------------------- |
| **全局对象**       | `window`                                    | `global`                                  |
| **模块系统**       | ES Module（原生）                           | CommonJS（默认） + ES Module              |
| **全局属性**       | DOM API (`document`, `location`, `history`) | I/O API (`fs`, `path`, `http`, `process`) |
| **顶层 this**      | `window`                                    | `{}`（模块作用域），非严格下也非 `global` |
| **事件循环阶段**   | 无明确定义的分阶段模型                      | 6 个阶段 + 微任务                         |
| **微任务执行时机** | 每个宏任务执行完后                          | 每个事件循环阶段结束后、进入下一阶段前    |
| **异步 I/O**       | 浏览器内核处理（fetch / XHR）               | libuv + 系统调用                          |
| **Worker**         | Web Worker（浏览器环境）、Service Worker    | `worker_threads` / `child_process.fork`   |
| **DOM 渲染**       | 有渲染管线，宏任务间可能穿插渲染帧          | 无，不涉及 UI 渲染                        |
| **微任务影响**     | 微任务过多会延迟渲染（长任务）              | 微任务过多会延迟下一个阶段                |

#### 核心相同点

- 都是 V8 引擎执行 JavaScript
- 都是**单线程**执行 JS 代码（用户代码）
- 都是**事件驱动 + 异步非阻塞 I/O**
- Promise / async/await / 微任务宏任务的行为一致
  :::

### 3.5 Node事件驱动、非阻塞机制的实现原理

::: details 参考

#### 核心模型：Event Loop + 观察者 + 请求对象

Node 的非阻塞 I/O 是**事件驱动**实现的，底层依赖 libuv 的 **Reactor 模式**。

#### 非阻塞 I/O 的完整流程

以一个 `fs.readFile()` 为例，追踪从 JS 调用到回调执行的完整路径：

```
1. JS 调用 fs.readFile('./data.txt', callback)
        │
2. Node Core API (fs.js) 封装参数，调用 C++ 绑定层
        │
3. C++ 绑定层 (node_file.cc) 创建 FSReqCallback 请求对象
        │
4. 将请求提交给 libuv 的线程池（Worker Thread）
   主线程立即返回，继续执行后续 JS 代码 ← 非阻塞的关键
        │
5. 线程池中的线程执行实际的阻塞 read() 系统调用
        │
6. read() 完成 → 线程将结果 + callback 封装后放入事件队列
        │
7. 事件循环 poll 阶段检测到该 IO 完成事件
        │
8. 调用 C++ 层的回调 → 触发 JS 层 callback(err, data)
```

#### 三种 I/O 处理方式

libuv 对不同 I/O 类型采用不同的处理策略：

| I/O 类型     | 处理方式                              | 示例                              |
| ------------ | ------------------------------------- | --------------------------------- |
| **网络 I/O** | 系统异步 API（epoll / kqueue / IOCP） | `http.get()`, TCP/UDP socket      |
| **文件 I/O** | 线程池（默认 4 线程）                 | `fs.readFile()`, `fs.writeFile()` |
| **DNS 查询** | 线程池 / c-ares 异步库                | `dns.lookup()`, `dns.resolve()`   |
| **加密压缩** | 线程池                                | `crypto.pbkdf2()`, `zlib.gzip()`  |

> 为什么文件 I/O 用线程池而不用 epoll？因为 Linux 的 epoll 对普通磁盘文件不完全支持异步——磁盘文件在操作系统层面总是"可读"的（即便数据还没从磁盘读到内存），epoll 无法正确反映实际 I/O 完成状态。所以 libuv 用线程池模拟异步文件 I/O。

#### 事件驱动架构实战

```js
const http = require('http')
const fs = require('fs')

const server = http.createServer()
server.on('request', (req, res) => {
  // 非阻塞：文件读取不阻塞其他请求
  fs.readFile('./large-file.dat', (err, data) => {
    res.end(data)
  })
  // 在等文件读取期间，事件循环可以处理其他请求
})
server.listen(3000)
```

#### 微任务在 Node 中的特殊行为

```js
// nextTick 在事件循环每个阶段切换前执行
// 递归 nextTick = 饿死事件循环（starve event loop）
function recursiveTick() {
  process.nextTick(recursiveTick) // 永远跳不出当前阶段，IO 回调饿死
}

// setImmediate 在 check 阶段执行，不会饿死 poll
function safeRecursive() {
  setImmediate(safeRecursive) // 每个 tick 给其他阶段执行机会
}
```

#### Node 的事件驱动本质

```

# Event-driven, Non-blocking I/O in Node

Node 的本质是一个**编排者**而不是执行者：

- 主线程（JS 线程）：负责编排任务、处理回调
- 线程池（Worker threads）：负责执行阻塞操作（文件 I/O、加密）
- 操作系统内核：负责异步 I/O（网络 epoll/kqueue）

这就是为什么 Node 擅长 I/O 密集型场景而非 CPU 密集型。CPU 密集型任务会占据主线程，阻塞所有 I/O 回调的执行。

对于 CPU 密集型任务，应该使用 `worker_threads` 将其卸到 Worker 线程中，保持主线程事件循环的健康运行。
:::
```
