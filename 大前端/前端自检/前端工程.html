包管理器的核心职责 ​

  1. 依赖解析：根据 package.json 计算完整的依赖树，处理版本冲突
  2. 依赖安装：下载并放置到 node_modules，处理跨平台兼容

幽灵依赖（Phantom Dependency） ​

npm/yarn 的扁平化提升机制会将间接依赖提升到顶层 node_modules，导致代码中可以 require/import 未在 package.json 中声明的包：

// 你的 package.json 只声明了 express
// 但 express 依赖了 cookie，被提升到顶层
// 这个 import 不会报错，但它是不可靠的！
import cookie from 'cookie'  // 幽灵依赖！

依赖解析算法 ​

1. 读取 package.json，收集顶层依赖列表
2. 对每个依赖，递归读取其 package.json 的 dependencies
3. 构建完整依赖图
4. 版本冲突时，npm 尝试安装多个副本（duplication）
5. 扁平化：尽量将依赖提升到顶层 node_modules
6. 生成 lock 文件记录所有精确版本

关键区别 ​

  • ESLint 不做代码转换，只做静态检查（代码 → AST → 检查规则 → 报告问题）

1.4 ESLint规则检测原理，常用的ESLint配置 ​

参考

ESLint 工作原理 ​

源代码 → 解析器(Parser) → AST → 遍历器(Visitor) → 规则检查 → 报告
1
  1. 解析器（Parser）：将代码解析为 AST。默认使用 Espree（ESLint 官方解析器），也可使用 @typescript-eslint/parser 处理 TS
  2. 遍历 AST：每个规则注册感兴趣的 AST 节点类型，遍历时触发回调
  3. 规则判断：规则在回调中检查节点是否符合要求（如 no-var 规则检查是否出现 VariableDeclaration(kind='var') 节点）
  4. 报告问题：用 context.report() 报告位置、消息、严重级别

自定义规则示例 ​

js
// 禁止使用 console.log 的规则
module.exports = {
  meta: {
    type: 'suggestion',
    messages: { unexpected: '不允许使用 console.log' }
  },
  create(context) {
    return {
      CallExpression(node) {
        if (
          node.callee.type === 'MemberExpression' &&
          node.callee.object.name === 'console' &&
          node.callee.property.name === 'log'
        ) {
          context.report({ node, messageId: 'unexpected' })
        }
      }
    }
  }
}

1.5 Babel的核心原理，可以自己编写一个Babel插件 ​

参考

Babel 三阶段 ​

源代码 → 解析(Parsing) → AST → 转换(Transformation) → 新AST → 生成(Code Generation) → 目标代码
1
  1. 解析（Parsing）
    • 词法分析：@babel/parser 将源码拆成 Token 流
    • 语法分析：消费 Token，按 ECMAScript 语法规则构建 AST
  2. 转换（Transformation）：插件遍历 AST，增删改节点（核心阶段）
  3. 生成（Code Generation）：@babel/generator 将 AST 还原为 JS 代码字符串

编写一个 Babel 插件 ​

以下插件将所有 console.log 调用替换为 console.warn：

js
// babel-plugin-convert-log-to-warn.js
module.exports = function () {
  return {
    name: 'convert-log-to-warn',
    visitor: {
      CallExpression(path) {
        const callee = path.node.callee
        if (
          callee.type === 'MemberExpression' &&
          callee.object.name === 'console' &&
          callee.property.name === 'log'
        ) {
          callee.property.name = 'warn'
        }
      }
    }
  }
}

核心 API ​

  • path.node：当前 AST 节点，可以修改

  • Preset：一组插件的集合（如 @babel/preset-env、@babel/preset-react）

关键阶段详解 ​

1. 编译（make 阶段）

  • 从 entry 开始，用对应的 loader 处理每个文件
  • 解析 import/require，收集依赖模块

  • 为每个 chunk 生成最终输出文件内容
  • 创建 assets，写入 dist/

HMR（Hot Module Replacement）热更新原理 ​

浏览器(WDS client) ←→ WebSocket ←→ webpack-dev-server
     │                                   │
     │  ① 文件变更                       │
     │                                   │  ② webpack 重新编译
     │                                   │  ③ 生成 hot-update 文件
     │  ④ 收到更新通知                   │
     │  ⑤ 请求 hot-update.json + hot-update.js
     │  ⑥ 执行更新代码，替换旧模块        │
     │  ⑦ 模块不可替换 → fallback 完整刷新 │

核心机制：

  • webpack-dev-server 通过 sockjs/WebSocket 与浏览器建立长连接
  • 文件变更时，webpack 增量编译生成 [hash].hot-update.json（chunk 映射）和 [hash].hot-update.js（增量代码）
  • 浏览器下载增量的模块代码，通过 module.hot.accept() 注册的回调重新执行
  • HMR 运行时利用 __webpack_require__ 的模块缓存机制，替换缓存的模块并重新执行

概念定义举例
module源码中的单个文件Header.tsx、utils.ts、style.scss

关系：n modules → 1 chunk → 1 bundle（或通过 mini-css-extract-plugin 拆成 JS + CSS 两个 bundle）

    proxy_pass http://backend;

算法对比 ​

算法原理适用场景
轮询（默认）依次分配，支持权重无状态、性能相近的后端

random随机分配简单场景

nginx 事件驱动架构 ​

nginx 高性能的核心是异步非阻塞事件模型：

  • Master 进程负责读取/校验配置、管理 Worker 进程
  • 每个 Worker 是单线程的，通过 epoll（Linux）/kqueue（macOS）同时监听数千个连接
  • 请求处理的各个阶段（accept、read、write）均注册回调，不会阻塞 Worker
  • 这也是为什么 worker_processes auto（匹配 CPU 核心数）和 worker_connections 会直接影响并发能力

Git 核心原理：内容寻址文件系统 ​

Git 本质是一个基于内容寻址（Content-Addressable）的文件系统，在此基础上实现版本控制。

核心对象模型（存在 .git/objects/ 中）：

对象类型作用内容

commit存储版本快照tree 引用、父 commit、作者、时间、提交信息
tag标记特定 commit指向 commit 的不可变引用（annotated tag 含额外信息）
commit --> tree --> blob (README.md)
              |--> blob (index.html)
              |--> tree --> blob (style.css)
              |        |--> blob (app.js)
              |--> tree --> blob (utils.js)

Git vs SVN ​

GitSVN
架构分布式（每人有完整仓库副本）集中式（单一中央仓库）
离线能力完整，可本地 commit/log/diff大部分操作需要连接服务器

为什么 Git 分支如此轻量 ​

SVN 的分支是服务器端目录的完整拷贝。Git 的分支只是一个指向某个 commit 的指针（文件 .git/refs/heads/branch-name 里就是一个 40 字节的 SHA），创建分支仅仅是写一个 41 字节的文件。

  • HTML 文件不做强缓存（Cache-Control: no-cache），JS/CSS 文件名带 hash 做永久缓存

  • 非覆盖式发布：新旧版本静态资源共存，HTML 更新即切换版本

6. 监控与告警 ​

上线后关注：

  • 错误率：JS Error / API Error 占比
  • 性能：Core Web Vitals（LCP / CLS / INP）
  • 可用性：页面可访问率、关键 API 成功率
  • 业务指标：核心流程转化率

告警规则示例：

  • JS 错误率 > 1% → 告警
  • API P95 响应时间 > 3s → 告警
  • LCP > 4s → 告警
