1 编译原理 ​

1.1 理解代码到底是什么，计算机如何将代码转换为可以运行的目标程序 ​

参考

代码是人类可读的、遵循编程语言语法规则的文本。计算机只能理解二进制机器码，代码本质上是程序员与硬件之间的抽象层。

通用编译流水线 ​

源代码 → 词法分析（Lexing/Tokenization） → Token 流 → 语法分析（Parsing） → AST（抽象语法树） → 语义分析 → 中间代码 → 优化 → 目标代码（机器码/字节码）

前端相关：V8 的 JIT 编译 ​

JavaScript 是解释型语言，但现代 JS 引擎使用 JIT（Just-In-Time）编译：

  1. Ignition（解释器）：将 AST 转为字节码并解释执行
  2. TurboFan（优化编译器）：识别"热代码"（频繁执行的函数），将其编译为高度优化的机器码
  3. 去优化（Deoptimization）：当类型假设被推翻时，回退到解释执行

V8 的"热代码检测"机制意味着函数被调用越多，执行越快。这也是为什么 V8 偏好"单态"（始终同类型）的代码 -- 类型变化会触发去优化。

前端工具链中的"编译" ​

  • Babel：源码到源码的转译器。解析 JS → AST → 按插件转换 AST 节点 → 生成兼容代码
  • TypeScript：TS 源码 → AST → 类型检查 → 擦除类型 → JS 输出
  • webpack：构建依赖图 → 生成 bundle 输出（本质是代码生成步骤）
  • Vite：开发阶段用 esbuild（Go 编写）做快速转译，生产用 Rollup

实践意义 ​

当你写 const x = 1，V8 分词得到 [Keyword, Identifier, Punctuator, NumericLiteral, Punctuator]，解析器构建 AST，再转字节码执行。理解这个流程有助于区分解析期错误（如 Unexpected token）和运行时错误。

1.2 正则表达式的匹配原理和性能优化 ​

参考

正则引擎类型 ​

类型特点使用场景
DFA（确定有限自动机）文本主导、无回溯、始终 O(n)、不支持反向引用awk、egrep
NFA（非确定有限自动机）正则主导、有回溯、支持惰性量词和反向引用JavaScript、Java、Python、Perl

前端开发者需要理解的是 NFA 引擎的回溯机制。

回溯机制 ​

NFA 一次尝试一条路径，匹配失败时回退到上一个决策点换一条路径重试：

  • 贪婪量词 * +：先尽可能多地匹配，然后逐字符回退
  • 惰性量词 *? +?：先尽可能少匹配，然后逐步扩展
  • 占有量词 *+ ++：尽可能多匹配，永不回退（JavaScript 原生不支持）

灾难性回溯（Catastrophic Backtracking） ​

javascript
// 危险模式：嵌套量词
/(a+)+b/.test('aaaaaaaaaaaaaaaaaaaaac')  // 指数级时间复杂度！

// 真实案例：URL 匹配
/(\/[\w-]+)+/.test('/a/b/c/d/e/f/g/h/i/j/no-match')

JS 中正则性能优化 ​

避免嵌套量词(a+)+ (a*)* 是危险信号

1.3 如何将JavaScript代码解析成抽象语法树(AST) ​

参考

什么是 AST ​

AST 是源代码的树状结构表示，每个节点代表一个语法构造（变量声明、函数调用、字面量等）。AST 剥离了格式细节（空格、注释），只保留语义结构。

JS 代码到 AST 的流程 ​

  1. 词法分析（Tokenizer/Lexer）：拆分源代码为 Token 流
    "const x = 42;" → [Keyword, Identifier, Punctuator, NumericLiteral, Punctuator]
    1
  2. 语法分析（Parser）：消费 Token 流，应用 ECMAScript 语法规则，生成 AST 节点

主流 JS 解析器 ​

工具特点
ESTree社区标准 AST 规范，ESLint/Babel 遵循
@babel/parser（原 Babylon）支持 JSX、TS、Flow、Stage 提案
Acorn轻量快速，webpack 内部使用
Esprima最早的 JS 解析器之一，ETree 兼容
TypeScript Compiler API微软出品，含类型信息

常见 AST 节点类型 ​

Program（根）、VariableDeclaration、FunctionDeclaration、ArrowFunctionExpression、CallExpression、MemberExpression、Literal、Identifier、IfStatement、BinaryExpression、TemplateLiteral、ImportDeclaration

AST 遍历与操作 ​

  • Visitor 模式：遍历节点时触发 enter/exit 回调
  • 修改节点：替换、插入兄弟节点、删除节点
  • 代码生成：将修改后的 AST 转回代码字符串

实践：写一个 Babel 插件 ​

javascript
import { parse } from '@babel/parser'
import traverse from '@babel/traverse'
import generate from '@babel/generator'

const code = 'const foo = bar(1, 2);'
const ast = parse(code)

traverse(ast, {
  CallExpression(path) {
    console.log('函数调用:', path.node.callee.name) // "bar"
  }
})

const output = generate(ast).code // "const foo = bar(1, 2);"

1.4 base64的编码原理 ​

参考

是什么，为什么 ​

Base64 将二进制数据编码为 64 个可打印 ASCII 字符（A-Z、a-z、0-9、+、/，= 填充）。目的是让二进制数据安全地通过只支持文本的协议（如 JSON、XML、HTTP 头、SMTP 邮件）。

编码算法（核心原理） ​

  1. 输入二进制数据，按字节（8 位）分组
  2. 每 3 字节（24 位）为一组
  3. 将 24 位拆分为 4 个 6 位组（$2^6 = 64$ 种可能值）
  4. 每个 6 位值映射到 Base64 字母表的一个字符
  5. 输入不足 3 字节时：缺 1 字节补 1 个 =，缺 2 字节补 2 个 =

示例：编码 "Man"

M (0x4D=77)  a (0x61=97)  n (0x6E=110)
01001101    01100001     01101110
010011  010110  000101  101110
19(T)   22(W)   5(F)    46(u)
→ "TWFu"

容量开销 ​

Base64 使数据增大约 33%（每 3 字节变成 4 字符）。这对前端决策有直接影响：

  • 小于 1KB 的小图标 → 适合内联为 data URL，减少 HTTP 请求
  • 大图片 → 应单独请求，不内联

JavaScript API ​

javascript
// 基础用法（仅支持 Latin-1 字符）
btoa('hello') // "aGVsbG8="
atob('aGVsbG8=') // "hello"

// Unicode 安全编码
function utf8ToBase64(str) {
  return btoa(
    encodeURIComponent(str).replace(/%([0-9A-F]{2})/g, (_, p1) => String.fromCharCode('0x' + p1))
  )
}

function base64ToUtf8(str) {
  return decodeURIComponent(
    atob(str)
      .split('')
      .map((c) => '%' + ('00' + c.charCodeAt(0).toString(16)).slice(-2))
      .join('')
  )
}

手动转换算法 ​

  • 十进制转 N 进制：反复除以 N，取余数，逆序排列
    • 42 → 十六进制：42÷16=2 余 10(A)，2÷16=0 余 2 → 0x2A
  • N 进制转十进制：每位数字 × $N^{position}$，求和
    • 0x2A = $2 × 16^1 + 10 × 16^0$ = 32 + 10 = 42

2 网络协议 ​

2.1 理解什么是协议，了解TCP/IP网络协议族的构成，每层协议在应用程序中发挥的作用 ​

参考

什么是协议 ​

协议是通信双方约定的规则集合，定义数据格式、时序、顺序和错误处理。如同语言：两边必须遵循相同约定才能正确交流。

TCP/IP 四层模型（前端该关注的视角） ​

层核心协议前端关联
应用层HTTP、HTTPS、WebSocket、DNS这是前端代码的工作层。fetch()、XHR、WebSocket API
传输层TCP、UDPTCP 可靠性决定资源加载质量；连接握手 + 慢启动影响首页速度
网络层IP、ICMP、ARPIP 路由决定数据包路径；CDN 基于 IP 就近选边缘节点
网络接入层以太网、Wi-Fi、4G/5G物理传输。移动网络延迟差异大（3G ~200ms vs 5G ~5ms RTT）

数据封装（Data Encapsulation） ​

每层把自己的头部加到上层数据前，像嵌套信封：

HTTP 请求 → [HTTP 数据]
      ↓ TCP 封装
[TCP 头 + HTTP 数据]（段/Segment）
      ↓ IP 封装
[IP 头 + TCP 头 + HTTP 数据]（包/Packet）
      ↓ 链路层封装
[帧头 + IP 头 + TCP 头 + HTTP 数据 + 帧尾]（帧/Frame）

2.2 三次握手和四次挥手详细原理，为什么要使用这种机制 ​

参考

三次握手（连接建立） ​

  |                              |

  |                              |

为什么是 3 次而不是 2 次？

防止历史连接请求导致半开连接。如果网络中滞留了一个旧的 SYN 包，服务端收 SYN 后直接进入连接状态，但客户端并未发起新连接——服务端资源泄漏。第三次 ACK 让服务端确认：客户端确实需要这次连接。

为什么双方都要同步序列号？

TCP 是全双工的——双方都需要初始序列号（ISN），确保后续数据传输能正确编号和确认。

DevTools 视角：Chrome Network 中 "Initial connection" = 1.5 RTT（SYN + SYN-ACK + ACK）。DNS 解析在握手之前。

为什么是 4 次而不是 3 次？

TCP 是全双工——每个方向的通道需要独立关闭。收到对方的 FIN 意味着"对方不发了"，但我方可能还有数据要发，所以我方的 FIN 可能在 ACK 之后单独发送。因此 ACK 和第 3 步的 FIN 不能合并。

TIME_WAIT 状态：主动关闭方等待 2×MSL（Maximum Segment Lifetime，通常 2 分钟），确保：

  1. 对端收到最后的 ACK（若对端没收到，会重传 FIN）
  2. 该连接的滞留包在网络中完全消失

前端关联 ​

2.3 有哪些协议是可靠，TCP有哪些手段保证可靠交付 ​

参考

可靠 vs 不可靠协议 ​

类型协议特性前端场景
可靠TCP有序、无丢失、无重复、无损坏HTTP、HTTPS、WebSocket、文件传输
不可靠UDP无送达保障，但低延迟DNS（主要）、WebRTC 媒体流、QUIC/HTTP3、在线游戏

TCP 可靠性的五大支柱 ​

① 序列号与确认（Sequence & Acknowledgment）

每个字节都有编号。接收方发送 ACK 告知"期望的下一个字节序号"。

发送方：字节 1-1000，seq=1，len=1000
接收方：ACK ack=1001（"收到了 1-1000，下一个发 1001"）
1
2

② 校验和（Checksum）

TCP 头部 16 位校验和覆盖伪首部 + TCP 头 + 数据。校验失败则静默丢弃该段（不发 ACK），触发重传。

③ 重传机制

  • 超时重传：发送后启动定时器，超时（RTO，基于 RTT 动态计算）未收到 ACK 则重发
  • 快速重传：发送方收到 3 个重复 ACK（说明后续包已到，中间丢了一个），不等超时立即重传

④ 流量控制（Flow Control / 滑动窗口）

接收方通告"窗口大小"（还能收多少字节）。发送方未被确认的数据量不能超过窗口大小。防止快发送方淹没慢接收方。

前端类比：Web Streams API 的背压机制（ReadableStream.pipeTo 的反压）、requestAnimationFrame 的帧率节流。

⑤ 拥塞控制（Congestion Control）

  • 慢启动：拥塞窗口 cwnd 从小开始，每 RTT 翻倍增长
  • 拥塞避免：达到阈值后线性增长
  • 丢包后：乘性减半（AIMD：Additive Increase Multiplicative Decrease）

这就解释了为什么页面资源加载速度呈"加速曲线"——前几个 KB 是最慢的（慢启动），这也是 HTTP/2 优先级和 preload 如此重要的原因。

前端影响总结 ​

机制解决的问题前端感知
Seq/ACK丢包、乱序保证 HTML/CSS/JS 完整到达
校验和数据损坏避免损坏资源
重传包丢失DevTools 中 "stalled" 请求
流量控制接收方溢出保护移动端弱设备
拥塞控制网络拥堵首页初始加载偏慢（慢启动）

2.8 HTTP1.1、HTTP2.0带来的改变 ​

参考

HTTP/1.1 的特点与痛点 ​

痛点原因前端的"奇技淫巧"
队头阻塞（HOL Blocking）同一连接请求必须按序处理，一个慢响应卡住全部浏览器开 6 个并发连接
Header 不压缩每次请求都完整发送头部（Cookie、UA 等），重复 500-800 字节无解
文本协议冗长、解析低效无解

HTTP/1.1 时代的优化 hack（在 HTTP/2 下反而有害）：

  • 域名分片：static1.xx.com、static2.xx.com 突破 6 连接限制 → HTTP/2 下单连接就够，多域名反而增加 DNS + 握手开销
  • CSS Sprites：所有小图合一张大图，background-position 裁切 → HTTP/2 多路复用后，独立小图更灵活
  • JS/CSS 合并打包：一个 bundle.js → HTTP/2 下按需按模块拆包更优，实现细粒度缓存
  • 内联（Inlining）：CSS/JS/SVG 内嵌 HTML → 无法独立缓存，增加 HTML 体积

HTTP/2 核心改进 ​

① 多路复用（Multiplexing） —— 关键特性

一次 TCP 连接上同时传输多个请求/响应。每个请求/响应被拆分为帧（frame），交叉发送，通过 Stream ID 在接收端重组。消除了应用层队头阻塞。

② Header 压缩（HPACK）

使用静态表（预定义的常见头 → 索引号）+ 动态表（记住之前出现的 header 组合）。后续请求只发索引号而非完整 header 字符串。大型 Cookie 的开销急剧降低。

③ 二进制分帧

HTTP/2 是二进制协议（非文本），解析更快、更少出错。对 fetch() 完全透明。

④ Server Push

服务端主动推送客户端未来可能需要的资源。Chrome 2022 年已移除支持（推送过度浪费带宽）。103 Early Hints 是更现代的替代。

⑤ 流优先级与流控

客户端可告知服务端优先级（"先发 CSS，后发图片"），支持逐流流控避免单一流独占连接。

HTTP/1.1 vs HTTP/2 策略迁移 ​

HTTP/1.1 策略HTTP/2 策略
域名分片合并为一个域名
CSS Sprites独立小图
JS/CSS 全量合并Code-split 按需加载
内联关键 CSS103 Early Hints
Cookie-free 域名HPACK 压缩下不需要

HTTP/3 (QUIC) 简览 ​

  • 基于 UDP 替代 TCP，消除 TCP 层队头阻塞
  • 内置 TLS 1.3 加密
  • 连接迁移：切换网络（Wi-Fi ↔ 蜂窝）连接不中断
  • 0-RTT 恢复连接（重复连接时）

2.9 HTTPS的加密原理，如何开启HTTPS，如何劫持HTTPS请求 ​

参考

为什么需要 HTTPS ​

HTTP 是明文传输，同网络（Wi-Fi、ISP）的任何人可阅读和篡改。HTTPS 提供三个保证：

  • 机密性（Confidentiality） —— 加密传输，无法窃听
  • 完整性（Integrity） —— 数据未被篡改
  • 身份验证（Authentication） —— 确认对方是真实的服务器

Service Worker、Geolocation API、HTTP/2 等新能力都需要 Secure Context（HTTPS 或 localhost）。

混合加密模型：非对称 + 对称 ​

非对称加密（TLS 握手阶段）：公钥/私钥对。公钥加密，私钥解密。作用是安全交换对称密钥 + 验证服务器身份。速度慢，不能用于大量数据。 → RSA、ECDHE（推荐，支持前向保密）

对称加密（数据传输阶段）：同一密钥加密解密。速度快。 → AES-GCM（带身份验证的加密）

HMAC（消息认证码）：检测数据是否被篡改。

TLS 1.3 握手过程（简化） ​

1. ClientHello  → 支持的密码套件、TLS 版本、随机数、密钥共享
2. ServerHello  ← 选中密码套件、随机数、密钥共享、证书（含服务器公钥）
3. 认证         → 客户端验证证书链（CA 签名 → 中间 CA → 根 CA）
4. 密钥协商     → 双方通过 ECDHE 独立计算相同的会话密钥
                  ★ 前向保密：即使服务器私钥泄露，历史会话密钥无法还原
5. Finished     → 双方确认握手完成，切换对称加密通信

TLS 1.3 = 1-RTT 握手，TLS 1.2 = 2-RTT。重复连接可 0-RTT 恢复。

证书与 PKI ​

  • CA（证书颁发机构）：可信第三方为域名签发证书。浏览器/OS 信任库包含约 150 个根 CA
  • 证书链：站点证书 → 中间 CA → 根 CA（必须在浏览器信任库中）
  • 证书类型：DV（域名验证，基本）、OV（组织验证）、EV（扩展验证，曾显示绿条，浏览器已移除）
  • 前端开发：mkcert 生成本地受信证书；Let's Encrypt 免费生产证书

开启 HTTPS（前端实践） ​

生产环境：

  • nginx/Apache 配置 SSL 证书，强制 HTTPS
  • 添加 HSTS 头：Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
  • HTTP → HTTPS 301 跳转

本地开发：

  • mkcert 生成开发用本地证书
  • Vite/CRA 内置 HTTPS 模式

迁移注意事项：

  • Mixed Content：HTTPS 页面的所有嵌入资源也必须 HTTPS。浏览器拦截 active mixed content（script），警告 passive（img）
  • CSP 升级：Content-Security-Policy: upgrade-insecure-requests 自动将 HTTP 升级为 HTTPS

降级攻击迫使客户端/服务器协商使用弱加密服务端禁用 TLS 1.0/1.1，最低 TLS 1.2，优先 1.3

  • net::ERR_CERT_AUTHORITY_INVALID → CA 不受信任（自签名证书）
  • net::ERR_CERT_DATE_INVALID → 证书过期
  • net::ERR_CERT_COMMON_NAME_INVALID → 域名不匹配
  • Chrome DevTools Security 面板 → 查看证书、加密套件、连接协议

2.10 理解WebSocket协议的底层原理、与HTTP的区别 ​

参考

什么是 WebSocket ​

全双工、持久的 TCP 连接，允许服务器实时向客户端推送数据，无需客户端轮询。RFC 6455 标准。URI 方案：ws://（明文）和 wss://（加密，基于 TLS）。

HTTP vs WebSocket 对比 ​

维度HTTPWebSocket
通信方式请求-响应（半双工）全双工双向
连接状态无状态（Keep-Alive 复用）有状态持久连接
发起方向仅客户端双方随时发送
每帧开销500-800 字节 Header2-14 字节
协议文本二进制分帧
适用场景文档传输、REST API实时数据、IM、协作编辑

数据帧结构（简化） ​

  • 字段：FIN（最后一帧）、Opcode（text/binary/ping/pong/close）、MASK（客户端→服务端必须 masking）、Payload 长度、Masking Key（4 字节）、Payload Data
  • Client→Server 掩码：客户端发的帧与随机 32 位 Key XOR 异或。防止缓存投毒攻击——恶意中间代理伪装缓存内容攻击。
  • 开销：仅 2-14 字节/帧 vs HTTP 的 500+ 字节

3.2 发布订阅模式和观察者模式的异同以及实际应用 ​

参考

两个模式常被混淆，本质区别在于耦合度 ​

观察者模式（Observer Pattern） ​

  • 结构：Subject（主题）直接维护 Observer（观察者）列表。Subject 知道 Observer 的存在。
  • 流程：Subject 状态变化 → Subject 直接调用每个 Observer 的 update() 方法
  • 耦合：有耦合——Subject 直接持有 Observer 引用

前端实例：

  • MutationObserver：监听 DOM 变化，直接回调
  • IntersectionObserver：监听可见性
  • Vue 响应式系统：数据的 getter/setter 直接通知 Watcher
  • RxJS Observable：observable.subscribe(observer)

发布-订阅模式（Pub-Sub Pattern） ​

  • 结构：Publisher 和 Subscriber 完全解耦，通过事件总线/消息代理（Event Bus/Broker）通信
  • 流程：Publisher → Publish 到 Channel → Broker 发消息给所有订阅该 Channel 的 Subscriber
  • 耦合：无耦合——Publisher 不知道谁是 Subscriber，Subscriber 不知道消息来自谁

前端实例：

  • DOM 事件系统：addEventListener('click', fn)，鼠标点击源不知道谁在监听
  • Node.js EventEmitter：emitter.on('event', fn) / emitter.emit('event', data)
  • Redux：store.subscribe(listener) / store.dispatch(action)
  • window.postMessage 跨窗口通信

核心差异表 ​

维度观察者模式发布-订阅模式
耦合度Subject 直接知道 Observer完全解耦，通过 Broker
通信方式Subject → Observer 直接Publisher → Broker → Subscriber
订阅方Observer 注册到 SubjectSubscriber 注册到 Broker（通过 Topic）
被通知方Subject 调用 observer.update()Broker 分发消息
类型关系一对多多对多

怎么选 ​

  • 观察者：有清晰的"数据源→依赖方"关系时使用。数据流清晰、易追踪（Vue 响应式、数据绑定、Direct Observer API）
  • 发布-订阅：不相干的模块间需要解耦通信时使用。微前端通信、跨组件事件、插件系统。EventBus 增加了间接层，但也方便了独立开发

RxJS 的 Subject 是两者的桥梁：它既是一个 Observer（可以 subscribe Observable），又是一个 Observable（可以被 subscribe），相当于流式编程中的事件代理。

3.3 可以说出几种设计模式在开发中的实际应用，理解框架源码中对设计模式的应用 ​

参考

各框架中的设计模式 ​

React：

  • 观察者模式：setState → 组件重新渲染。状态是 Subject，组件是 Observer
  • 组合模式：React 组件树。叶子（普通元素）和组合（容器组件）共享统一接口（render / JSX）
  • 工厂模式：React.createElement(type, props, children) 创建 VNode
  • 装饰器模式：HOC（connect、memo、withRouter）
  • 责任链模式：事件冒泡——事件沿组件树上传，每个处理者可消费或传递

Vue：

  • 代理模式：Vue 3 的 reactive() 基于 ES6 Proxy，拦截属性读写实现依赖收集
  • 观察者模式：模板渲染函数是 Effect（观察者），响应式数据是 Subject（被观察者）
  • 策略模式：编译器策略——web 编译与 SSR 编译使用不同编译策略；DOM 操作的不同 Patch 策略
  • 装饰器/插件模式：Vue.use(plugin) 为 Vue 实例增加功能
  • 管道/中间件模式：Vue Router 导航守卫（beforeEach → beforeResolve → afterEach）

Angular：

  • 依赖注入模式：核心模式——Service 被注入到 Component，不需要手动 import
  • 装饰器模式：@Component、@Injectable、@Input、@Output 都是装饰器

状态管理库：

  • Flux/Redux：命令模式（Action 是命令对象封装状态变更数据）+ 观察者模式（store.subscribe()）
  • MobX：观察者模式——可观察对象自动追踪观察者，精准更新
  • Zustand：单例/模块模式——Store 是模块级单例，通过选择器订阅

构建工具：

  • Babel：访问者模式（Visitor Pattern）——遍历 AST，每个节点类型触发对应回调
  • webpack Loader 链：责任链/管道模式——style-loader!css-loader!sass-loader 依次处理
  • webpack Plugin Hooks：观察者模式——compiler.hooks.done.tap('MyPlugin', callback)，Tapable 机制
  • webpack Target：策略模式——target: 'web' / 'node' / 'webworker' 不同输出策略

设计模式认知的意义 ​

不需要"为了用模式而用模式"。真正的价值在于：

  1. 阅读框架源码时能理解为什么这么写
  2. 与团队沟通时能简洁描述设计意图
  3. 重构时能识别出应该用什么模式来降低复杂度

好的设计模式让代码更简单，而不是更复杂。如果引入一个模式后代码变得更难理解了，那可能用错了或不应该用。
